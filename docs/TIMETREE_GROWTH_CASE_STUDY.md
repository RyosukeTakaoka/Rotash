# TimeTree — 成長事例からの構造抽出と Rotash への応用

`GROWTH_STRATEGY.md` セクションH、および [`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md) の続き。
今回扱う TimeTree は、あすけん（個人の日々の習慣アプリ）ともH章の海外SNS事例とも違う、
**「複数人で1つの共有オブジェクトを編集し続ける」**という、Rotashに最も構造が近いアプリである。

**Rotashとの構造的な近さ：** TimeTreeもRotashも「1人のためのツールではなく、
複数人が同じ1つのオブジェクト（カレンダー／7分割の作品）を共同で育てる」設計である。
だからH章の海外SNS事例より、**参考にすべき示唆の密度が高い。**

## 1. 招待が「機能」ではなく「作成の続き」である設計 — M1が既に正しい方向にある証拠

TimeTreeでは、**カレンダーを作った直後に招待画面が出る**。
「後で友達を呼ぶ」のではなく、**カレンダー作成というフロー自体の最終ステップとして招待がある。**
招待方法もメール・SMS・QR・URLの4経路が用意されており、相手の環境を選ばない。
[（出典）](https://www.sungrove.co.jp/timetree-share/)

### Rotashへの示唆：M1の設計方針を裏付ける、実務上の追加ポイント

これは `GROWTH_STRATEGY.md` D-2・M1（招待をリンク＋未完成作品画像にする）と**同じ方向**であり、
新しい発見というより**強い裏付け**である。1点、実装の参考になる違いがある：

> TimeTreeは招待経路を1つに絞らず、**相手が最も受け取りやすい経路（メール/SMS/QR/URL）を
> 選ばせている。** Rotashの現在の想定（`UIActivityViewController` 経由）も結果的に複数経路（LINE、
> メッセージ、AirDrop等）をカバーするが、**「その場にいる相手にはQR」「離れた相手にはURL」という
> 使い分けをUIとして明示していない。**

**→ 判定：SHOULD（M1実装時の追加考慮点）。** 新しいMUSTを増やすものではなく、
M1のUI設計時に「その場で見せる（QR）」と「送る（URL）」を1つのシェアシートに任せず、
招待画面自体に軽く使い分けを示す価値がある。ただし優先度はM1本体より低い。

## 2. 予定というオブジェクトにコメント・写真が残る — Rotashが最初から持っている資産

TimeTreeの各予定には、**コメントと写真を残せる。**
「◯月◯日 家族旅行」という予定が、単なる日時の情報ではなく、
**後から見返す思い出の入れ物になる。** カップルの記念日や家族旅行の記録として使われている実例が多い。
[（出典）](https://fukucale.ai/labo/time-tree/how-to-use)

### Rotashへの示唆：これは既にRotashの設計思想そのものである

`GROWTH_STRATEGY.md` A-2 が言う「7分割の作品が、進捗・成果・証拠という3つの役割を同時に果たす」
という考え方は、TimeTreeの「予定がスケジュールであり同時に思い出の入れ物である」という設計と
**同じ原理**である。**新しい示唆は無い。** ただし、この一致は重要な確認になる：

> TimeTreeのような7,000万人規模のプロダクドでも、**「管理のための道具」と「思い出のための場所」を
> 分けずに1つのオブジェクトに統合する**ことが、長期利用を支える設計として機能している。
> Rotashが7分割という1つのオブジェクトに進捗・成果・証拠を全部乗せる判断（分離しない）は、
> 大規模プロダクトの実例と整合している。

**→ 判定：確認のみ（変更提案なし）。** `GROWTH_STRATEGY.md` L-6 の定義を補強する事例として引用できる。

## 3. 「上限を外して用途を広げる」— Rotashが意図的に選ばなかった道

TimeTreeは最大200人・20カレンダーまで対応することで、**個人 → 家族 → カップル → 仕事**と、
**同一プロダクトのまま利用シーンを広げてきた。**
利用ガイドも `usages/category/family-partner` のようにシーン別に多数用意されている。
[（出典）](https://timetreeapp.com/intl/ja/usages/category/family-partner)

### Rotashへの示唆：これはRotashが辿るべき道ではないことを、他社事例で再確認する

一見「Rotashも人数上限を緩めて、サークル全体やイベント全員が使えるようにすれば、
TimeTreeのように成長できるのでは」という誘惑が生まれる。**しかし結論は逆である。**

| | TimeTree | Rotash |
|---|---|---|
| コアの価値 | **予定管理という機能的価値**（Functional）。人数が増えても価値は薄まらない、むしろ便利になる | **1人では完成しない、という希少な制約**（Network Value、`GROWTH_DIAGNOSIS.md` §5） |
| 上限を外すと | 使えるシーンが増える（会議カレンダー、掃除当番など） | **希少性が消える。7枠が7枠でなくなった瞬間、Locket的な"特別感"（H-2）が壊れる** |
| 200人カレンダーの実態 | 「便利な道具」として使われる（仕事のシフト表等） | 同じことをすると、「今日は誰？」の不確実性が薄まり、**当番表アプリになる**（J-1 #1と同じ死因） |

TimeTreeが上限を外せたのは、**そもそもFunctional Valueで戦っているから**である。
Rotashは `GROWTH_DIAGNOSIS.md` §5 が明記する通り **Functional Valueが最も弱く、
Network Valueが最も強い**プロダクトであり、TimeTreeとは価値の源泉が逆である。

**→ 判定：この比較そのものが結論。新しい施策は生まれない。**
`GROWTH_STRATEGY.md` L-4（DON'T）の「複数グループ（上限3）」は LATER のまま据え置き、
**「上限そのものを外す」方向は永久に検討しない**ことをこの事例で明文化しておく。
TimeTreeは反面教師ではなく、**「なぜ自分たちは違う道を選んだか」を説明する材料**として使う。

## 4. フリーミアム＋広告という収益モデル

TimeTreeは基本機能を無料開放し、広告収入で運営しながら、2022年に「TimeTreeプレミアム」
（月額300〜480円）を追加した。広告非表示・カレンダー数拡張・AIスケジューリングが有料機能である。
[（出典）](https://timetreeapp.com/intl/ja/newsroom/2022-04-19/timetree-premium)

またLPの再設計だけでサブスク課金率を2.5倍に改善した事例も報告されている
（ユーザーの課題を軸にプロダクトを運営する、という原則から）。
[（出典）](https://markelabo.com/n/n5ae43af8e862)

### Rotashへの示唆：広告は導入しない。プレミアムの方向性だけ参考にできる

Rotashは現在マネタイズ設計を持たず、`GROWTH_DIAGNOSIS.md` も「90日でやらないこと」に
マネタイズ設計を含めている。この判断は変えない。ただし将来のための整理として：

- **広告は導入しない。** `GROWTH_STRATEGY.md` J-2 が禁じる「作品が外部評価の対象になる」流れと
  同様に、広告が作品の周りに挟まると「自分たちの1週間」という没入感が壊れる。BeRealが
  ブランドを入れて壊れた道筋（H-1）と同種のリスクである
- **有料化するとしたら、あすけんケーススタディ§4/§5と同じ結論に戻る**：
  コア体験（3〜7人での週次完走）は無料のまま提供し、**複数グループ（LATER項目L2）や
  Memoriesの高度な表現など、コアを損なわない拡張だけを課金対象にする**

**→ 判定：LATER。既存のマネタイズ方針（当面設計しない）を変更する材料ではない。**

## 5. 「みつける」機能 — 蓄積データを次の体験に変える動き

2026年1月、TimeTreeは10年分の「予定」という蓄積データを土台に、
**「みつける」という発見・レコメンド機能**を追加した。
「共有カレンダー」から「未来の行動選択のプラットフォーム」への進化と位置付けている。
[（出典）](https://zuuonline.com/archives/301034)

### Rotashへの示唆：時期尚早だが、方向性としては記憶しておく

これは典型的な**データフライホイール型の拡張**であり、Rotashにも将来的な類似の芽がある：

> 何十週分ものMemoriesが積み上がったグループが増えたとき、
> 「過去のこの季節、こんな1週間を作っていた」を**Memories内で振り返らせる**、
> あるいは`AssignmentPlanner`の担当順アルゴリズムを、蓄積データから
> 「予測不能性」がより高くなるよう調整する、といった拡張がありうる。

ただしこれは**10年・7,000万人分のデータがあって初めて意味を持つ**施策である。
Rotashは開発7日・ユーザー実質0人（`GROWTH_DIAGNOSIS.md` §1）の段階であり、
**今これを検討するのは明確に時期尚早。**

**→ 判定：LATER（さらに後方）。** `GROWTH_STRATEGY.md` L-3 の「LATER」群よりもさらに先、
グループの継続週数が十分に蓄積してから（L4「Memoriesの作品数に応じた表現の変化」と統合して
検討する程度）。90日計画には一切含めない。

## 6. まとめ

| 節 | 判定 | 既存資料との関係 |
|---|---|---|
| §1 招待が作成の続きである設計 | **SHOULD**（M1実装時の考慮点） | D-2・M1を裏付け。経路の使い分けUIを補強 |
| §2 予定＝思い出の入れ物 | **確認のみ** | L-6の定義（7分割が進捗・成果・証拠を兼ねる）を大規模事例で裏付け |
| §3 上限を外して用途拡張 | **反面教師として明文化** | L-4（複数グループDON'T/LATER）の理由を強化。**Rotashが選ばなかった道を、他社の成功例と対比して説明できるようになった** |
| §4 フリーミアム＋広告 | **LATER**（広告は不採用） | マネタイズ設計は90日計画の対象外のまま |
| §5 「みつける」的データ活用 | **LATER（さらに後方）** | L3/L4よりも先の将来課題 |

**この資料の結論：**
TimeTreeはRotashに最も構造が近い事例でありながら、**最大の学びは「真似ないこと」の理由づけ**
だった。TimeTreeが200人・20カレンダーまで上限を外して成長できたのは、
Functional Valueで戦っているからであり、**Network Valueで戦うRotashが同じことをすると、
唯一の武器（1人では完成しない）を自分で手放すことになる。**

一方で、招待導線（§1）と「1つのオブジェクトに全部を乗せる」設計（§2）は、
**Rotashが既に正しい方向で設計・計画していることの独立した裏付け**になった。
[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md) と合わせて、
**2つの全く性質の違うプロダクト（個人向け習慣アプリ／複数人共有ツール）を見ても、
GROWTH_STRATEGY.md の結論が揺らがなかった**ことが、この2本の資料が持つ最大の価値である。
