# Defensibility Map — 「アイデア」ではなく「模倣困難な仕組み」

[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md)〜[`FRAME_CHANGE_STRATEGY.md`](FRAME_CHANGE_STRATEGY.md) までの5本は、
「他社の成功事例から何を借りるか」「Rotash自身の前提をどう変えるか」を扱ってきた。

この資料は問いの立て方が違う。**「Rotashが成功した後、競合が完全にコピーしたら何が残るか」**
を先に考える。三井越後屋の「現金掛け値なし」が単体の発明ではなく、店頭販売・現金取引・定価・
切り売り・新しい顧客層・広告・検証を一体化した**相互依存する仕組み**だったからこそ、
競合が値下げだけを真似ても同じ経済構造にはならなかった——という指摘に基づく。
（このフレーム自体はユーザーからの分析提供。本資料はそれをRotashの現状のコードと
既存Docsに照らして具体化したものである。）

**結論を先に書く。** Rotashは「アイデア」（1人では完成しない、7分割、今日は誰？）は
かなり強い。しかし**「競合が同じアイデアを実装した後も勝てる構造」はまだ無い。**
これは弱点の指摘ではなく、**Pre-PMFの現段階では当然**である
（`GROWTH_DIAGNOSIS.md` §2-1：これはGrowthの問題ではなくPre-PMFの問題）。
だからこの資料は「今すぐ全部作れ」ではなく、**PMF検証と並行して"見る"べき地図**として書く。

---

## 1. もし競合がコピーしたら

2027年、Instagram・BeReal・Locketのいずれかが「友達7人で1週間、1枚ずつ撮って作品を完成させる」
機能を追加したと仮定する。**この時点でRotashは危険な立場になる。**
大手には既存ユーザー・通知基盤・写真保存基盤・ソーシャルグラフ・App Store上の認知・
開発人員が既にある。**「7分割というUIだけ」で戦えば、Rotashは負ける。**

7分割UIも「1日1人」という制約も、実装難易度は低い。特許も取れない。
`GROWTH_STRATEGY.md` H章が分析した競合（BeReal・Locket・Wordle・Duolingo・Snapchat・
Pokémon GO）は「機能」ではなく「構造」を比較していたが、
**その構造さえも、大手が本気でコピーすれば数週間で実装できる。**

**→ だから「アイデアの独自性」に安住してはいけない。** 求めるべきは、
コピーされても揺るがない**5つの層**である。

## 2. 防御の5層

### 層①：Rotashでしか成立しない習慣 — 「イベント×7日間」への埋め込み

現在のRotashは「毎週続く」という構造は正しい（`rollWeekIfNeeded()`、
`GROWTH_STRATEGY.md` B章）。しかし**「なぜ今週も続けたいか」の理由**はまだ弱い。

目指す状態は、Rotashが「アプリ」ではなく**「7日間かけて何かを追う儀式」**になることである。

```
旅行なら：
月：旅行準備を撮る　火：買ったもの　水：荷造り　木：移動
金：到着　土：旅行本番　日：帰宅

文化祭・部活の合宿・卒業・修学旅行でも同じ構造が使える
```

`GO_TO_MARKET.md` は既に「何かに向かう1週間」を最初の獲得単位として重視している
（本資料はこの方向を否定せず、一段深掘りする）。**ここまで行けば、
競合が機能をコピーしても、ユーザーの生活に入り込んだ「習慣の中身」まではコピーできない。**

### 層②：作品の蓄積 — Memoriesが「この7人の人生の断片」になる

`GROWTH_STRATEGY.md` C-2（Memoriesの積層表示）は正しい方向にある。
将来的には「1週目→2週目→…→1年」という**蓄積そのものが資産**になる設計を目指す。

重要な釘刺し：これは`PRODUCT_PHILOSOPHY.md`が既に整理している通り
**CREATE → REMEMBER**（作ってから、後で振り返る）という順序を守ること。
**REMEMBER起点（過去を振り返らせるための機能）を先に作らない。** 今週の1本を作ることが
先で、蓄積はその副産物として積み上がる。

### 層③：7人の関係そのもの — 「所属感」はまだ薄い

`YOUTH_NEEDS.md` の自己診断（Connection→○、Belonging→×、Contribution→×）は
かなり正直で重要な指摘である。現状Rotashが提供しているのは「つながり」までで、
**「俺らのRotash」という所属感、「自分が貢献した」という実感**はまだ設計されていない。

これは新しいMUSTを増やす提案ではない。既存の`GROWTH_STRATEGY.md` E-3（タイトルを
つける行為）が「アプリ内で唯一の能動的な行為」として既に狙っている領域であり、
**この所属感の弱さは、既存のMUST（M1〜M5）が実装された後に効いてくる次の課題**として、
ここで明示的に記録しておく。

### 層④：データではなく「関係の履歴」

「この7人は52週間で31作品作った」というデータは、単なる利用統計ではなく
**共同制作の履歴**になる。`GROWTH_STRATEGY.md` C-3 は既にグループの作品数を
「数えるが目立たせない」と定めており、この方針とも整合する。

**釘刺し（既存資料の再確認）：** 誰が何回撮ったか・何週続いたかを**ランキング化しない**。
`GROWTH_STRATEGY.md` J-1 #2（個人の撮影率・貢献度の可視化は相互監視を生む）が
既に明確に禁じている通りである。**「私たちがどれだけ一緒に作ったか」**であって
**「誰が一番頑張ったか」**ではない。

### 層⑤：Distributionそのものを製品にする — 視覚言語のブランド化

`GROWTH_STRATEGY.md` E章（フィルムストリップとしての共有画像）は既にこの方向にある。
目指す最終状態は、**「Rotashで作った」と書かなくても、見ただけでRotashだと分かる**こと——
Appleのロゴを消してもAppleのデザインだと分かるのと同じ強さである。

これはE-3〜E-5が既に定めている「広告ではなく作品として見せる」「キャプションを提供しない」
という原則そのものであり、**新しい提案ではなく、この原則を守り切ることの重要性の再確認**
である。三井越後屋の暖簾・風呂敷・傘（使っているだけで宣伝になる道具）に相当するのが、
Rotashにとってはこの**7分割という視覚的な文法**である。

## 3. Defensibility Map

**このマップは、GROWTH_DIAGNOSIS.mdのMonth 3以降、四半期に一度更新することを想定する。**

| 資産 | コピー難易度 | 現在 | 1年後（目標） |
|---|---|---|---|
| 7分割UI・1日1人という制約 | 低 | ○（実装済み） | △（大手が模倣していても不思議はない） |
| 「今日は誰？」の不確実性演出 | 低〜中 | △（通知未実装、M4待ち） | ○ |
| ブランド化された視覚言語（フィルムストリップ） | 中 | ×（M2未実装） | ○ |
| イベント×7日間という利用習慣 | 高 | ×（構想段階） | △ |
| Memoriesの積層＝グループ史 | 高 | ×（S1未実装） | △〜○ |
| 「この7人」という所属感 | 高 | ×（YOUTH_NEEDSが自己診断済み） | △ |
| グループの関係履歴（週数・作品数の蓄積） | 非常に高 | ×（データ自体が無い） | △ |
| ユーザー間の実際の人間関係 | 非常に高 | △（7人という単位はあるが履歴が無い） | △〜○ |

**読み方：** コピー難易度が低い資産（UI・制約）は、MUST（M1〜M5）を実装すればすぐ○になるが、
**大手が本気を出せば同じスピードで追いつかれる。** 逆にコピー難易度が高い資産（習慣・所属感・
履歴）は、**今は何も無いが、時間をかけてしか作れない分、一度できれば数年単位で追いつかれない。**
→ **MUSTの実装で満足せず、コピー難易度が高い層への投資を止めないこと**がこの表の結論。

## 4. 20グループ実験を「市場発見」として再設計する

`GROWTH_DIAGNOSIS.md` Month 2 は既に「出来事の種類をわざとバラす」実験設計を持っている
（「出来事なし」を2グループ含む）。この資料は、それを**固定4分類・各5グループの
比較実験**として精緻化する提案である。

| 群 | 内容 | グループ数 |
|---|---|---|
| A | ただの1週間（出来事なし・対照群） | 5 |
| B | 旅行 | 5 |

見る指標（`GROWTH_DIAGNOSIS.md` K-3 の補助指標をそのまま使う）：

| 指標 | A | B | C | D |
|---|---|---|---|---|
| 3人到達率 | | | | |
| 7日完走率 | | | | |
| 2週目継続率 | | | | |
| 撮影率（担当日に実際に撮った割合） | | | | |
| 完成作品のShare率 | | | | |
| 新規グループ発生数（K） | | | | |

**この表が埋まると分かること：** 「Rotashは何に使われるプロダクトなのか」が実数で分かる。
例えば旅行群の完走率が90%で、日常群が30%なら、**Rotashは「日常写真アプリ」ではなく

`GROWTH_DIAGNOSIS.md` 仮説4（出来事依存）への回答を、より解像度高く出せる設計である。

**→ 判定：`GROWTH_DIAGNOSIS.md` Month 2 の実行方法を、この4群構成に更新することを提案。**
既存の「出来事なし2グループ」という対照群の考え方は維持しつつ、群のラベル付けを
事前に固定4分類にすることで、後から見た時の分析精度が上がる。

## 5. Phase別のボトルネックを先読みする

三井型の思考は「成功した後」を先に逆算することでもある。Rotashが各フェーズに到達したとき、
何が律速になるかを今のうちに書き出しておく（**実装するという意味ではない。備える対象を
明確にするだけ**）。

| フェーズ | 規模 | 想定される律速 |
|---|---|---|
| Phase 0（現在） | 20グループ | PMF未検証（`GROWTH_DIAGNOSIS.md` の通り） |
| Phase 1 | 100グループ | Firestoreセキュリティルール未整備のまま公開範囲が広がるリスク（既存`S5`） |
| Phase 2 | 1,000グループ | Firebase/Cloudinaryのコスト。画像ストレージが線形に増える |
| Phase 3 | 10,000グループ | サポート体制（問い合わせ対応の人力限界） |
| Phase 4 | 100,000グループ | 不正・なりすまし対策。App Store検索での埋没（ASO） |
| 未知の変化点 | — | 「学校単位で一斉導入される」「1人が複数Rotashを掛け持ちする」（`GROWTH_DIAGNOSIS.md`が既にLATER扱いとしている複数グループ対応と接続）「イベント会社が営業目的で使い始める」「競合が本格参入する」 |

**→ 判定：新しい実装課題ではない。** `GROWTH_DIAGNOSIS.md` の90日計画（Phase 0の検証）を
最優先としつつ、**Phase 1のセキュリティルール（S5）だけは、20グループを超えて公開範囲が
広がる前に必ず先行させる**という優先順位の確認として記録する。

## 7. まとめ

三井越後屋の教訓は「良いアイデアを思いつく」ことではなく、
**アイデア・オペレーション・コスト構造・顧客層・販売方法・広告・効果測定を一体化する**
ことだった。Rotashに置き換えると、`GROWTH_STRATEGY.md`〜`GROWTH_DIAGNOSIS.md`は
「アイデア」と「初期の販売方法（GTM）」と「効果測定の仕組み（Firestore集計、K指標）」
までを既にかなり深く設計している。**足りないのは新しい機能ではなく、
①〜⑤の層を「一つの模倣困難なシステム」として統合する視点**である。

そしてこの統合は、今日実装するものではない。**まず20グループの実験（§4）で
「Rotashが一番強くなる状況」を発見し、その発見をもとに、どの層に最初に投資すべきかを
決める**——これが、三井型の「仕組み」を作るための、Rotashにとって現実的な最初の一歩である。
