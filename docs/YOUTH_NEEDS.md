# Rotash — 若者の欲求と、成長への効き方

「若者の欲求を満たす機能を追加する」のではなく、
**すでに Rotash が持っている心理構造のうち、どこが空いているかを特定して、そこだけ埋める**ための資料。

前提は [`IMPLEMENTATION_PLAN.md`](IMPLEMENTATION_PLAN.md)（何を入れて何を入れないか）と
[`GROWTH_DIAGNOSIS.md`](GROWTH_DIAGNOSIS.md)（律速はどこか）。

---

## 0. この資料の使い方 — 層は「足す場所」ではなく「測る場所」

欲求を9段に分解すると、**各段に機能を1つ足したくなる。**
9つ足したら Rotash は死ぬ。だから最初に運用ルールを1つ置く。

> **層は、機能を足す場所ではない。どこが詰まっているかを測る場所である。**

そして診断の形は `GROWTH_DIAGNOSIS.md` と同じになる。

```
欲求そのものは失敗しない。失敗するのは、欲求と欲求のあいだの変換である。
```

Layer 1 → 9 には**8本のリンク**があり、それぞれに変換率がある。
プロダクトの仕事は「欲求を満たすこと」ではなく、**変換率がほぼ0のリンクを見つけて直すこと**。

## 1. 欲求の階層と、現在の充足状況

先週の実装（`IMPLEMENTATION_PLAN.md` の N2〜N6）で、どこが埋まって、どこが空いたか。

| | 層 | Rotash での形 | 現状 |
|---|---|---|---|
| L1 | **Connection**「つながっていたい」 | 7人で1つを作る | ◯ 構造として最初からある |
| L2 | **Belonging**「自分たちはこのメンバー」 | グループ名だけ | **× ほぼ空** |
| L3 | **Contribution**「自分もこれを作った」 | 撮ったあと、痕跡が残らない | **× ほぼ空** |
| L4 | **Identity**「これが私たち」 | 週のタイトル（N5） | △ 入ったばかり |
| L5 | **Memory**「この時間を残したい」 | Memories の積層（N6） | ◯ |
| L6 | **Anticipation**「明日は誰？」 | 朝8時の通知（N4） | ◯ |
| L7 | **Pride**「私たちが作った」 | 完成画面（N5） | ◯ |
| L8 | **Sharing**「見せたい」 | 9:16 の共有画像（N3） | ◯ |
| L9 | **Invitation**「お前らもやろう」 | 招待リンク（N2） | ◯ |

### ここから読めること

**L4〜L9 は先週すべて何かが入った。空いているのは L2 と L3 だけである。**

そして重要なのは、**L3（Contribution）が L1・L2 と L4 以降をつなぐ蝶番**だということ。

```
L1 つながりたい  →  L2 このメンバーだ  →  L3 自分も作った  →  L4 これが私たち
                                          ↑
                                  ここが空いていると、
                                  「7人の作品」ではなく
                                  「誰かが作った7枚」になる
```

自分が撮った1枚が、完成した作品のどこにあるのか **アプリが一度も示していない**。
撮った直後は自分の写真が枠に入るので分かるが、翌日には7枚のうちの1枚に紛れる。

> **提示された案のうち、本当に新しいのは「自分の痕跡（Your shot）」ひとつで、
> それがちょうど、いま最も空いている層に当たっている。**

## 2. 提示された5施策の棚卸し

「私なら追加するのはこの5つ」に挙がったもののうち、**3つは先週すでに実装済み**である。

| 施策 | 状態 | どこ |

これは分析が間違っていたのではなく、**既存構造がすでに欲求の多くを拾っていた**ことの裏付けになる。

## 3. 5列の優先順位表

重点検証したいとされた6つの欲求について、
**① 欲求 → ② 既存機能 → ③ 新機能候補 → ④ Growth Loop への効き方 → ⑤ 検証 KPI**。

| 欲求 | ② 既存機能 | ③ 新機能候補 | ④ Growth への効き方 | ⑤ 検証 KPI |
|---|---|---|---|---|
| **貢献**<br>Contribution | 撮影・担当日 | **自分の担当を作品内で見分けられるようにする**（アプリ内のみ） | **R**（自分の週が「自分ごと」になれば翌週も撮る） | **担当日の撮影率**<br>＝ 自分の当番日に実際に撮った割合。<br>**今日から測れる** |
| **内輪感**<br>Inside joke | 週のタイトル（N5） | なし（追加しない） | **K**（外から意味が分からない一行が「これ何？」を生む） | **タイトル記入率** ＋ **外部に意味が通じないタイトルの割合**（目視分類）。<br>**今日から測れる** |
| **憧れ**<br>Aspiration | 9:16 の共有画像（N3） | なし（追加しない） | **K そのもの** | **K**（`?from=` 経由で立ち上がったグループ数）。<br>N2 が動き出せば測れる |
| **期待**<br>Anticipation | 朝8時の通知（N4）・未来の担当を伏せる | なし（追加しない） | **完成率 → R** | 撮影時刻が朝の通知後に寄るか（部分的）。<br>**厳密にはアプリ側の起動計測が要る** |
| **思い出**<br>Memory | Memories の積層（N6）・archive | 1年前リマインド（**今は作れない**） | **R**（長期） | 3週以上続いたグループ数。<br>Memories 閲覧率は**現状測れない** |
| **所属**<br>Belonging | グループ名のみ | 保留（L2 は空だが、埋め方が分かっていない） | **R** | **定量指標なし。インタビューで聞く** |

### この表から出る、運用上の結論

**6つのうち、今日から数字で追えるのは3つだけ**（貢献・内輪感・憧れ）。
残り3つは**インタビューか、アプリ側の起動計測が要る**。

だから Phase 0 では、

- **貢献・内輪感・憧れ** → `tools/rotash-stats.py` と目視分類で追う
- **所属・期待・思い出** → 20人インタビューで聞く（`PRODUCT_PHILOSOPHY.md` 30 の質問に混ぜる）

数字が出ないものを無理に数値化しない。**測れないことを認めるほうが、偽の指標を作るより安全である。**

## 4. 新しい2案の評価

### 4-1. 自分の痕跡（Your shot）

**狙う層：L3 Contribution。いま最も空いている。**

ただし、そのまま実装すると Rotash の核と衝突する。

| やり方 | 判定 | 理由 |
|---|---|---|
| 自分の写真を大きく表示する | **不可** | 7分割の等分が崩れる。「7人で1つ」が「自分＋6人」になる |
| 「あなたのベストショット」等の評価 | **不可** | 写真が評価対象になる（`IMPLEMENTATION_PLAN.md` NEVER） |
| **共有画像で自分の枠を強調する** | **不可** | 7人が7通りの画像を出すことになり、**「この7人が作った1つ」が崩れる** |
| **アプリ内で、自分の名前だけ明度を上げる** | **可** | 情報を足すのではなく、**すでに出ている名前の読み分け**にすぎない |

> **アプリ内では自分の痕跡を見せてよい。共有画像では見せてはいけない。**
> 前者は所属の確認、後者は作品の分裂だから。

**実装の規模：1行。** `ThisWeekView` の担当者名は現在すべて `Palette.faint` で、
自分の枠だけ `Palette.text` にすればよい。新しい UI 要素は増えない。

**ただし、いま入れるかは別問題。**
「自分の貢献が見えない」という不満は**まだ誰からも出ていない**。
`N1`（人数 cap）を保留にしたのと同じ理由で、**最初の20グループのインタビューで聞いてから**でよい。
1行なので、必要と分かってから入れても遅くない。

### 4-2. 1年前の作品リマインド

**狙う層：L5 Memory。**

**今は作れない。** プロダクトが生後7日で、1年前のデータが存在しない。
機能を書いても1年間テストできず、その間に前提が変わる。

**繰り延べのコストはゼロである。** `archive` は週を消さずに全部持っているので、
いま何もしなくても、1年後には必要なデータが揃っている。**今やるべきことは「消さないこと」だけ。**

そして提示された懸念（「思い出アプリにしすぎない」）は正しい。

```
Retro    REMEMBER
Rotash   CREATE → REMEMBER
```

**Rotash の主役は現在進行形の制作**で、思い出は結果として積み上がるもの。
順序が逆になると、Retro との差別化を失う。

## 5. 追加で NEVER に入れるもの

提示された指摘から、禁止リストに1つ足す。

| 機能 | なぜ |
|---|---|
| **週の写真コンテスト / ベストショット投票** | 「今週一番いい写真を決めよう」を入れると、**写真が上手い人が中心になり、友達と作る体験が壊れる**。Rotash が狙うのは Social Competition ではなく **Social Cooperation** |

そして関連して、既存の NEVER の理由づけが1つ強くなる。

**いいね・ランキングを入れない理由は「作品が評価対象になるから」だけではない。**
Rotash の承認は **「評価された」ではなく「貢献した」で満たす**設計であり、
評価軸を持ち込むと、この2つが競合して弱いほう（貢献）が必ず負ける。

## 6. ポジショニング — 孤独を解消するアプリにしない

Rotash が狙うべきなのは、

- ✕ オンライン上に新しい人間関係を大量に作る
- ⭕ **すでにある現実の友達関係を、もう一段深くする**

これは `GO_TO_MARKET.md` のビーチヘッド（ライブ仲間・部活・ゼミ）と完全に一致する。
**既にグループになっている人たちを探すのは、そこにしか Rotash の価値がないからでもある。**

### 参照した調査

| 出典 | 内容 | 確認状況 |
|---|---|---|
| [Pew Research Center (2025.04)](https://www.pewresearch.org/internet/2025/04/22/teens-social-media-and-mental-health/) | 10代の **74%** が SNS で友達の生活とのつながりを感じる一方、**31%** が「人気の投稿をするプレッシャー」、**31%** が「友達から除外されている」と感じる | **一致を確認済み** |
| [こども家庭庁「こども・若者の意識と生活に関する調査」](https://www.cfa.go.jp/resources/research/chilren-attitudes) | 学校で出会った友人と、インターネット上の人とで「楽しく話せる」「つながりを感じる」「本音を話せる」に大きな差 | **調査と設問の実在は確認。個別の数値は未確認** |

> **数値の精度に結論は依存しない。**
> 「現実の友人関係のほうが濃い」という向きが正しければ、Rotash の方針は変わらない。
> ただし資料に数字を書くときは、確認済みかどうかを分けておく。

## 7. まとめ

1. **欲求リストを増やしても、施策リストは増えなかった。** 5案のうち3つは実装済み、
   1つは今は作れない、残る1つは1行の変更である。**既存構造がすでに欲求の多くを拾っている。**

2. **空いているのは L2 Belonging と L3 Contribution の2つだけ。**
   L3 は「自分の名前の明度を上げる」1行で触れる。L2 は**埋め方がまだ分かっていない**ので、
   機能を当てずにインタビューで聞く。

3. **6つの欲求のうち、今日から測れるのは3つ**（貢献＝担当日の撮影率、内輪感＝タイトル記入率、
   憧れ＝K）。残りはインタビュー。**測れないものを無理に数値化しない。**

4. **層は足す場所ではなく測る場所。** この資料を「9つの機能を作る根拠」として使わないこと。
