# Rotash — 成長戦略・習慣化・バイラルループ設計

この資料は「Rotashをどう流行らせるか」ではない。

**「Rotashを使うこと自体が、次のRotashを生み出す構造」をどう作るか**の設計書である。

前提として [`docs/PRODUCT_PHILOSOPHY.md`](PRODUCT_PHILOSOPHY.md)（なぜこう作ったか）と
[`README.md`](../README.md)（今どう実装されているか）を読んでいること。

この資料は現在のコードを実際に読んだ上で書かれている。
「あるべき論」ではなく「今どうなっていて、何が欠けているか」を起点にしている。

> **この資料が扱うのは「ループが回り始めた後」である。**
> ループにまだ何も乗っていない状態（リリース直後）から最初の1周をどう作るかは
> [`docs/GO_TO_MARKET.md`](GO_TO_MARKET.md) を参照。
> 後述の成長条件 `R + K > 1` は、**ループに何かが乗って初めて意味を持つ式**であり、
> それだけでは Phase 0 の指針にならない。

## 0. 最初に：前提の訂正

戦略に入る前に、**現在の実装と、開発者が信じている前提との間にある3つのズレ**を先に潰す。
ここを直さないと、以降のすべての施策が空振りする。

### 0-1. 「7人必要」は、現在のRotashには存在しない

Rotash最大の武器だと考えられているのは、

> 1人では作品が完成しない。だから6人を誘う。

という制約である。

**しかし現在のコードには、この制約が一切実装されていない。**

- `AppViewModel.createRotash()` は作成者1人だけでグループを成立させる
- `WeekPlanner` / `AssignmentPlanner` は1人グループでも問題なく動く
  （README: 「条件を全部は満たせない場合（1人グループなど）でも、進行不能にならないよう段階的に条件を緩めて必ず割り当てます」）
- README: 「3人なら 月A 火B 水C 木A 金B 土C 日A と一巡し続ける」

つまり **今のRotashは、1人でも7枚を完成させられる。**
しかも、その状態でアプリは何の警告も出さない。

これは単なる実装漏れではない。**現状の最悪のシナリオが静かに起きる。**

```
Aが Rotash をつくる
↓
招待コード R7K2M9 が出る
↓
LINEで友達に送る（誰も入らない）
↓
月曜「今日は A」
火曜「今日は A」
水曜「今日は A」
...
↓
「今日は誰？」が「今日も自分」になる
↓
コア体験が完全に死んだまま、アプリは正常に動き続ける
↓
Aは「別に面白くないな」と思って離脱する
```

Rotashが検証したがっている仮説（「今日は誰？が楽しいか」）は、
**1人グループでは絶対に検証できない。** それなのに、アプリはそれを許している。

**→ これが現在の最大の欠陥。以降の全施策の前提として最優先で潰す。**

### 0-2. ただし「7人を必須にする」のは間違い

では6人集まるまでアプリを動かさなければいいのか。**それは違う。**

初期の6人招待ゲートは、あらゆるソーシャルアプリを殺してきた典型的な失敗である。

- 招待する側は、6人が入るまで**何も見られない**（価値を体験する前に労働を要求される）
- 誘われる側は、**まだ何も入っていない空のキャンバス**を見せられて「入って」と言われる
- 6人中5人しか入らなければ、そのグループは永久に始まらない
- グループ作成から開始までのリードタイムが数日になり、その間に熱が冷める

**正しい設計は、7を「下限（floor）」ではなく「定員（cap）」として扱うこと。**

| | floor（必要人数）として扱う | cap（定員）として扱う ← 推奨 |
|---|---|---|
| 意味 | 「7人集めないと始まらない」 | 「7人までしか入れない」 |
| 感情 | 義務・ノルマ・面倒 | 希少・特別・限定 |
| 招待の動機 | 埋めないと始まらないから | この人と一緒に作りたいから |
| 失敗時 | グループが永久に始まらない | 少人数で普通に始まる |
| 誘われた側 | 「6人分の穴埋め要員」 | 「7枠のうちの1つに選ばれた」 |

Locketが「親しい友達20人まで」で成功し、Pathが「150人まで」でカルト的支持を得たのは、
**上限が membership を希少財に変えるから**である。
下限は入場料であり、上限は招待状である。

**Rotashの人数設計（決定）:**

- **最小 3人** — これがコア体験の成立ライン
- **理想・定員 7人** — 「7日 = 7人 = 1人1日」の完全形
- **1人・2人 = 未開始状態** — アプリが明示的にそう扱う

なぜ3人が最小ラインか。

「今日は誰？」の面白さは、**不確実性 × 観客時間**で決まる。

| 人数 | 「今日は誰？」の不確実性 | 自分が観客でいる割合 |
|---|---|---|
| 1人 | ゼロ（毎日自分） | 0/7 |
| 2人 | 五分五分（すぐ飽きる） | 約 3/7 |
| **3人** | **予測不能になる** | **約 5/7** |
| 7人 | 完全に予測不能 | 6/7 |

3人でようやく「予測できないこと」が体験になり、
自分が観客でいる時間が制作者でいる時間を上回る。
**Rotashが「撮るアプリ」ではなく「見るアプリ」になる境界が3人。**

### 0-3. 「完成したらゲームが終わる」問題は、実は最大の課題ではない

開発者は「7枚完成した瞬間にゲームが終わる」ことを最大の課題候補として挙げている。

**しかし実装を読む限り、この心配は構造上ほぼ解決済みである。**

`AppViewModel.rollWeekIfNeeded()` は月曜になると**自動的に**次の週を生成し、
前の週を Memories に落とす。ユーザーが「新しい週を作る」操作は存在しない。

つまり Week 2 は **オプトインではなくオプトアウト**である。
継続がデフォルトで、止めるには能動的にアプリを消す必要がある。これは正しい。

**本当の問題は「終わってしまうこと」ではなく、「終わったことに誰も気づかないこと」である。**

現状、日曜の夜に7枚目が入っても：

- 完成通知は飛ばない（通知機構が存在しない）
- 完成画面もない（縦画面に「今週の作品ができました」というテキストが1行出るだけ）
- 完成した作品は、翌月曜に静かに Memories へ移動する
- 誰もシェアしない

**1週間かけて7人で作った唯一の成果物が、何の儀式もなく消える。**
これはRetentionの問題ではなく、**バイラルの問題**である。次章で扱う。

## A. Growth Loop の分解

### A-1. 11の問いへの回答

Rotashのループを1周させるには、11の異なる動機が連続して成立する必要がある。
**それぞれについて「今それが成立しているか」を実装ベースで判定する。**

| # | 問い | 動機の正体 | 現状 |
|---|---|---|---|
| 1 | 誰が最初に始めるか | 「言い出しっぺ」体質の1人。グループの中心人物。 | ○ |
| 2 | なぜ始めるか | 新しいものを試したい + **仲間に見せたい**。開始自体が社交行為。 | ○ |
| 3 | なぜ6人を誘うか | **今は理由がない**（1人で完成するから） | **×** |
| 4 | 誘われた人はなぜ参加するか | 断るコストのほうが高い + 「7枠のうちの1つ」の希少性 | **△** 希少性が未表現 |
| 5 | 何に価値を感じるか | 自分の1日が、他人の6日と並んで意味を持つこと | ○ |
| 6 | なぜ毎日開くか | 「今日は誰？」+「何を撮った？」 | **×** 通知なし・きっかけなし |
| 7 | なぜ担当日を楽しみにするか | 6日待って回ってくる希少な発言権 | ○ 構造として成立 |
| 8 | なぜ完成させたいか | 自分が抜けると穴が空く（作品への責任） | **△** 穴の痛みが未表現 |
| 9 | なぜシェアしたいか | **今は理由がない**（シェア物が魅力的でない） | **×** |
| 10 | 見た人がなぜやりたくなるか | 「これ何？」→ 自分たちの1週間も見たい | **×** ブランド表現ゼロ |
| 11 | なぜ翌週も続けるか | 止める理由がない（自動継続）+ 作品が増える喜び | ○ 構造は成立 |

**×が4つ、△が2つ。しかも×は「招待」「毎日開く」「シェア」「これ何？」という、
ループの接続部にすべて集中している。**

現在のRotashは、**個々の体験は良いが、体験と体験の間がつながっていない。**
機能が足りないのではなく、**接続が足りない。**

### A-2. ループの構造 — 3つの入れ子

Rotashのループは1本ではない。**同じ1つのオブジェクト（7分割の作品）を中心に、
回転速度の違う3つのループが入れ子になっている。**

```
                    ┌──────────────────────────────────────┐
                    │        外側：バイラルループ（週次）      │
                    │                                      │
                    │   完成作品 → SNS → 「これ何？」        │
                    │        ↑                    ↓         │
                    │        │              新しい7人組     │
                    │        │                    │         │
        ┌───────────┼────────┴──────┐             │         │
        │           │  中間：週次ループ │             │         │
        │           │                │             │         │
        │      日曜 完成 → 振り返り → 月曜 新しい担当順        │
        │           ↑                │             │         │
        │  ┌────────┴──────┐         │             │         │
        │  │ 内側：日次ループ │         │             │         │
        │  │                │         │             │         │
        │  │  朝「今日は誰？」 │         │             │         │
        │  │      ↓         │         │             │         │
        │  │   待つ・想像する │         │             │         │
        │  │      ↓         │         │             │         │
        │  │  「◯◯が撮った」 │         │             │         │
        │  │      ↓         │         │             │         │
        │  │   見る → 1枚増えた        │             │         │
        │  │      ↓         │         │             │         │
        │  └──→ 翌朝へ ─────┘         │             │         │
        │                             │             │         │
        └─────────────────────────────┘             │         │
                    │                               │         │
                    └───────────────────────────────┘─────────┘
                              同じ7人が翌週も回る
```

**この入れ子構造が、Rotashが機能を増やさずに成長できる理由である。**

7分割の作品という**1つのオブジェクトが、3つの役割を同時に果たしている**：

| ループ | 作品の役割 | ユーザーが見ているもの |
|---|---|---|
| 日次 | **進捗** | 埋まっていく途中経過 |
| 週次 | **成果** | 完成した1つの作品 |
| バイラル | **証拠** | 「この7人が同じ1週間を生きた」記録 |

普通のアプリなら、進捗バー・完成画面・シェア画像は別々に作る。
**Rotashはそれが全部同じ7分割である。** これは極めて強い設計上の資産であり、
以降のすべての施策は「この1つのオブジェクトを3方向に磨く」ことに集約される。

## B. Week 1 → Week 2 の設計

### B-1. 構造は既に正しい。欠けているのは「区切り」

前述の通り、週送りは自動である。だから設計すべきは「継続させる仕組み」ではなく、
**「1周が終わったことを、全員が同時に、気持ちよく認識する仕組み」**である。

なぜ区切りが要るのか。**区切りのない継続は、継続ではなく惰性になる。**

惰性は、以下の理由で必ず途切れる：

- 途切れたことに誰も気づかない（気づかれないなら戻る理由もない）
- 積み上がった感覚がない（10週続けても「なんとなく続いている」だけ）
- 誰も「来週もやろう」と言わない（言うタイミングがない）

### B-2. 設計：日曜の夜 20 分間

**7枚目が入った瞬間、または日曜 21:00（どちらか早い方）にトリガーする。**

```
日曜 20:47 — Gが最後の1枚を撮る
      ↓
全員に1通だけ通知：「今週の作品ができました」
      ↓
開くと、初めて "完成形" が現れる
```

ここで見せるものは、**今まで6日間見ていた進行中のキャンバスとは、意図的に別物にする。**

| 進行中（THIS WEEK） | 完成形（THE WORK） |
|---|---|
| 画面いっぱいの7分割 | **余白の中に置かれた7分割** |
| 曜日ラベル + 担当者名 | 週の日付 + 7人の名前 + ROTASH |
| 空き枠がある | 完結している |
| 「作りかけ」 | **「作品」** |

進行中は画面を埋め尽くし、完成形は余白に浮かぶ。
**これだけで「終わった」が伝わる。** テキストで「完成しました！」と書く必要はない。

### ただし「終わった」を伝えすぎてはいけない

完成の演出を強くするほど、**「これで一区切り」という感覚も強くなる。**

そして [`GO_TO_MARKET.md`](GO_TO_MARKET.md) 3章の通り、初期のグループは
「◯◯までの7日間」という出来事を理由に立ち上がる。その出来事は7日目に終わる。
**出来事の終わりと作品の完成が同じ日に重なると、二重の終止符になる。**

だから完成画面で作品を**単独で見せてはいけない。**
**Memories の積層の一番上に、今週の1本が載る瞬間**として見せる。

```
     終わった、に見える            1本増えた、に見える

   ┌─────────────┐          ▐███|██|█|███|██▌   ← 先週
   │             │          ▐█|███|██|█|███▌   ← 先々週
   │  ■■■■■■■   │          ─────────────────
   │             │          ▐■■|■■|■|■■|■■▌   ← 今週（新しく載る）
   └─────────────┘
    作品が1つ、宙に浮く         列が1本伸びる
```

1週目のグループには積む先がないので、そこだけは単独で出してよい。
**2週目以降、完成画面は必ず「積層 + 今週」になる。**
これが S1（Memories の積層表示）を SHOULD ではなく M3 と同時に作る理由でもある。

そして完成画面には **SHARE だけ**を置く。
「来週も続ける？」というボタンは**置かない**（後述）。

### B-3. なぜ「来週も続ける？」を聞いてはいけないか

これは重要な設計判断である。

「Week 2 に進むか？」を明示的に問うUIは、**継続率を必ず下げる。**

- 問われるまで「やめる」という選択肢は存在しなかった
- 問われた瞬間に、それは**決断すべき事柄**になる
- 7人のうち1人でも「今週はいいかな」と押したら、グループが欠ける
- 全員のYesが必要な設計は、人数が増えるほど成立確率が下がる（0.9^7 = 0.48）

**正しいのは、月曜の朝に「今日は◯◯」がただ届くこと。**

ユーザーは決断していない。ただ、いつもの朝が来ただけである。
**Week 2 は「始める」ものではなく、「気づいたら始まっている」ものにする。**

これは現在の `rollWeekIfNeeded()` の実装思想そのものであり、
**変更してはいけない。守るべき資産として明記しておく。**

### B-4. Week 1 → Week 2 の完全な流れ

```
日曜 20:47  最後の1枚が入る
日曜 20:47  通知「今週の作品ができました」（1通・全員）
日曜 20:48  完成形を見る（余白の中の7分割）
日曜 20:49  SHARE → Instagram / LINE
              ↓
              ここで外側のバイラルループへ分岐
              ↓
月曜 00:00  rollWeekIfNeeded() が静かに走る
            前週は Memories へ（1本増える）
            新しい担当順が内部で決まる（誰にも見えない）
月曜 08:00  通知「今日は MINA」
              ↓
            Week 2 の日次ループが、何の決断もなく始まっている
```

**日曜夜と月曜朝の間に、ユーザーの意思決定は1つも挟まっていない。**
挟まっているのは「シェアするかどうか」だけであり、それは継続ではなく拡散の判断である。

## C. 「同じ7人で続ける」の設計

### C-1. 継続の報酬を「連続週数」にしてはいけない

セクションCへの回答の核心はここにある。

継続を可視化する方法は2つある。**この2つは似て見えて、真逆の心理を生む。**

| | **連続週数（streak）** | **作品の枚数（collection）** ← 推奨 |
|---|---|---|
| 増え方 | 続ければ +1 | 続ければ +1 |
| **減り方** | **1週休むとゼロに戻る** | **絶対に減らない** |
| 働く心理 | 損失回避（失う恐怖） | 獲得（積み上げの喜び） |
| 1週休んだ時 | 「もう終わりだ」→ 完全離脱 | 「今週は3枚だったな」→ 翌週復帰 |
| 主体 | 個人の記録 | **グループの資産** |
| 行き着く先 | **義務** | 蓄積 |

Duolingoのstreakは日次リテンションを2倍にする強力な機構だが、
**同社が「ストリークフリーズ」「ストリーク復活」という救済策を大量に実装している事実**が、
streakの本質的な欠陥を証明している。**壊れた瞬間の痛みが大きすぎて、そのまま帰ってこない。**

Rotashは**7人全員に依存する**。1人が旅行に行けば No Shot が出る。
7人のうち誰か1人がコケるだけで連続が切れる設計は、
`0.95^7 = 0.70` — 毎週30%の確率でグループ全体の記録が壊れる。**破綻している。**

さらに致命的なのは、streakが**相互監視を生む**ことだ。
「お前のせいで連続が切れた」が発生した瞬間、Rotashは共同制作から相互監視のツールに変わる。
これは開発者が最も避けたい「義務化」そのものである。

**→ 連続週数は実装しない。DON'T に分類する。**

### C-2. 代わりに：Memories を「積層」にする

**継続の報酬は、数字ではなく面積で与える。**

現在の Memories は、7分割サムネイル (`WeekThumbnailStrip`) の縦リストである。
これは既に正しい方向にある。**あと一歩、"リスト" を "積層" に変える。**

```
現在（リストに見える）              変更後（積層に見える）

MEMORIES              3
                                  MEMORIES
2026.08.03 - 08.09
[A|B|C|D|E|F|G]                   ▐█|██|█|███|██|█|██▌
                                  ▐██|█|███|█|██|███|█▌
2026.07.27 - 08.02                ▐█|███|██|█|███|█|██▌
[A|B|C|D|E|F|G]                   ▐███|█|██|███|█|██|█▌
                                  ▐██|███|█|██|█|███|██▌
2026.07.20 - 07.26                ▐█|██|███|█|██|███|█▌
[A|B|C|D|E|F|G]                              ⋮

日付が主役。作品が従。          作品が主役。日付は消す（タップで出る）。
3本が「3項目」に見える。        12本が「1つの厚み」に見える。
```

日付ラベルを各行から外し、間隔を詰め、**帯を密着させて積み上げる。**

- 3本 → 「まだ始まったばかり」
- 12本 → 「もう3ヶ月やってる」
- 30本 → **「これはもう、このグループの歴史だ」**

数字を1つも出さずに、継続が**視覚的な厚みとして**伝わる。
そして**この積層自体が、7分割というRotashのブランド表現の反復になっている。**
Memories画面を人に見せるだけで「何これ」が起きる。

**これが「グループそのものがソーシャル資産になる」の実装である。**

### C-3. 継続要素の扱い方 — 個別判定

セクションCで挙げられた各要素の扱いを決める。

| 要素 | 扱い | 理由 |
|---|---|---|
| **担当順** | **毎週変える。ユーザーには見せない。** | 変わることが「新しい週」の実体。予測不能性がコア資産。現在の `AssignmentPlanner` は「前週とまったく同じ並びを避ける」を既に実装済み。**触らない。** |
| **担当曜日** | 固定しない | 「毎週水曜は自分」になった瞬間、Rotashは当番表になる。カレンダーアプリ化はコアの死。 |
| **前週の写真** | Memories からのみ。THIS WEEK には出さない | 今週のキャンバスに先週が混ざると「1週間 = 1作品」の単位が壊れる。 |
| **Memories** | **積層表示にする（C-2）** | 継続の唯一の報酬装置。ここに全部を集約する。 |
| **グループの作品数** | 数える。ただし**目立たせない** | `archive.count` は既にある。Memories 見出しの脇に小さく置く現状の扱いが正しい。バッジ化・目標設定は禁止。 |
| **連続週数** | **実装しない** | C-1 の通り。 |
| **グループの年齢** | 「2026.06 から」を Memories の末尾に1行だけ | 増え続けるだけで、絶対に減らない。損失回避が働かない継続表現。 |

### C-4. 「この7人で続けたい」を生む唯一の感情

機能の話をやめて、感情の話をする。

**「この7人で続けたい」は、機能では作れない。**
作れるのは**「この7人でしか作れなかったものが、目の前にある」という状態**だけである。

だから設計目標は1つに絞れる：

> 完成した作品を見たとき、
> **「これは自分ひとりでは絶対に作れなかった」**
> と分かること。

7枚のうち6枚は、自分が見たことのない景色である。
自分がいた場所と、6人がいた場所が、同じ1本の帯に並んでいる。

これが伝わるための条件は3つ：

1. **写真が多様であること** — 全員が自撮りなら「7人分の顔」であって「1週間」にならない
   （PRODUCT_PHILOSOPHY 5, 21 で既に最重要検証項目として認識されている通り）
2. **誰が撮ったか分かること** — 名前がないと、7枚が誰のものでもなくなる
3. **同時に見えること** — 7分割が1画面に収まっているから比較が起きる。すでに実装済み

**1が最大のリスク。** 撮影画角が狭く自撮りに偏るなら、
バイラルもRetentionも成立しない。**成長施策より前に、この検証が先に来る。**
（→ セクション I-13、LATER の「撮影画角の分離」）

## D. 「1人では完成しない」を武器にする

### D-1. 制約が効いてくる仕組み

`1人では作品が完成しない` という制約は、**5つの異なる場所で同時に効く。**
だからこの制約1つを正しく実装するだけで、5つの指標が同時に動く。

```
        ┌─────────────────────────────────┐
        │  1人では作品が完成しない          │
        └────────────┬────────────────────┘
                     │
   ┌────────┬────────┼────────┬─────────┐
   ↓        ↓        ↓        ↓         ↓
 招待率   バイラル  継続率    FOMO    グループ形成
   │        │        │        │         │
「誘わな  「6人が  「自分が  「今週も  「7人という
 いと始  一緒に   抜けると  自分抜き  単位が
 まらな   入る」   穴が空く」 で進んで  最初から
 い」              　        いる」    存在する」
```

**重要なのは、この5つが全部「招待して」というお願いを一度も経由しないこと。**

普通のアプリの招待：

```
アプリを使う → 満足する → 「友達を招待しませんか？」 → 面倒 → 無視
                                    ↑
                            アプリの都合。ユーザーの都合ではない。
```

Rotashの招待：

```
作品を作りたい → 7枠ある → 埋めたい → 友達を呼ぶ
                                        ↑
                        ユーザー自身の目的。アプリは何も頼んでいない。
```

**「友達を招待する」ではなく「作品を完成させるために友達が必要」**という状態は、
**招待を機能ではなく手段にすることで達成される。**

つまり Rotash の招待画面は、**招待画面であってはいけない。**
「作品に7枠あり、まだ空いている」という**作品の状態表示**でなければならない。

### D-2. 実装：招待状は「未完成の作品」そのもの

現在の招待は `InviteCodeView` で6桁コードを表示してコピーさせるだけである。

```
現在：
  「R7K2M9」をコピー → LINEに貼る → 送信
  → 受け取った側が見るもの：ただの6文字
  → 「何それ？」
  → 説明する必要がある（招待者に労働が発生する）
```

**これを、作品の画像そのものに置き換える。**

```
変更後：
  「7枠のうち、まだ空きがある」を画像にする
  → 受け取った側が見るもの：

      ▐  |  |  |  |  |  |  ▌     ← 空の7分割（または途中まで埋まった実物）
        MON TUE WED THU FRI SAT SUN
        2026.09.07 - 09.13
        RYO ・ 空 ・ 空 ・ 空 ・ 空 ・ 空 ・ 空

      「この1週間を、一緒に1枚にしない？」
      rotash.app/j/R7K2M9

  → 説明不要。見れば分かる。
  → 「7枠のうち1つに呼ばれた」が伝わる
```

**この1つの変更が、招待の性質を根本から変える。**

| | 6桁コード（現在） | 未完成の作品（変更後） |
|---|---|---|
| 受け手が最初に見るもの | 意味不明な6文字 | **プロダクトそのもの** |
| 招待者の労働 | 説明が必要 | ゼロ |
| 参加までの手数 | DL → 参加 → コード入力 → 名前 | **リンク → DL → 名前** |
| 感情 | 「作業」 | 「選ばれた」 |
| 断りやすさ | 断りやすい | **枠が空いたままになるので断りにくい** |

**技術的に必要なもの（MUST）:**

- `Info.plist` に URL Scheme（`rotash://join/R7K2M9`）または Universal Link
  — **現在 `CFBundleURLTypes` は存在しない**（`.rotash` ファイルのUTIのみ定義済み）
- 招待時に現在の週の状態を画像化する（`WorkExporter.contactSheetURL` を空枠込みで流用可能）
- 共有シートに「画像 + テキスト + リンク」の3点を渡す

### D-3. 「あと◯枠」の見せ方

定員7に対する空き枠を、**煽らずに**見せる。

```
やってはいけない：
  「あと4人招待して作品を完成させよう！」  ← ノルマ。アプリの都合。
  「⚠️ メンバーが足りません」               ← エラー扱い。

正しい：
  縦画面に、今週のメンバーを淡々と並べる

    MEMBERS                    3 / 7
    RYO   MINA   KEN
    ─     ─      ─      ─

  空き枠を「―」として、ただ置く。
  文言はゼロ。タップすると招待の共有シートが開く。
```

**空白は、それ自体が最も強い招待メッセージである。**
7つ並ぶはずの場所に3つしかない状態を見せるだけでいい。
説明した瞬間にノルマになる。

### D-4. 3人未満のときだけ、明示的に扱う

0-1 で指摘した「1人グループが静かにコア体験を殺す」問題への対処。

**1〜2人のときは、Rotashを「開始前」として扱う。**

```
1〜2人のとき：
  - 縦画面：「今日の担当」を出さない（自分しかいないので意味がない）
  - 代わりに：MEMBERS 1 / 7 と、空の7分割
  - 横画面：7分割は見せる（何を作るのか分かる）が、
            「まだ始まっていない」ことが分かる状態にする
  - 撮影は可能にしておく（試せないと魅力が伝わらない）

3人目が入った瞬間：
  - 全員に通知：「3人になりました。今日は◯◯」
  - ここから正式に日次ループが始まる
```

**重要：撮影を禁止してはいけない。** 1人でも撮れる状態は残す。
禁止すると「触れないアプリ」になり、誘う前に離脱する。
変えるのは**演出**だけである。「今日は誰？」を1人グループで演出しない。

これは実装コストが小さく（表示分岐のみ）、
かつ 0-1 で指摘した最悪シナリオを直接潰す。**MUST。**

## E. 完成作品を Growth Engine にする

### E-1. Wordle の教訓 — 成長したのはゲームではなく、共有形式

セクションHに属する話だが、Eの前提として先に置く。

Wordleは**共有機能を追加した後、2ヶ月で90人から300万人になった。**
[（出典）](https://slate.com/culture/2022/01/wordle-game-creator-wardle-twitter-scores-strategy-stats.html)

しかも、あの緑と黄色のマス目を発明したのは開発者ではない。ユーザーである。
開発者がやったのは、**ユーザーが既にやっていた共有を、1タップにしたことだけ**である。

あの絵文字グリッドが機能した理由は3つ：

1. **一目でそれと分かる**（緑と黄色のマス＝Wordle、他の何にも見えない）
2. **答えを明かさない**（見た人は「自分でやるしかない」）
3. **説明が要らない**（投稿者は何も書かなくていい）

**Rotashの7分割は、この3条件を満たしうる数少ないビジュアルである。**
横一列に並んだ7つの細長い写真は、他の何にも見えない。

**しかし現在の実装は、この資産を捨てている。**

### E-2. 現在の共有実装の問題（コードを読んだ上での指摘）

`WorkExporter.swift` を読むと、深刻な問題が2つある。

#### 問題1：コンタクトシートが 16:9 横長で、Instagramに載らない

```swift
let panelWidth = ((height * 16 / 9) - gapTotal) / CGFloat(count)
// height = 1080 → 出力は 1920 × 1080
```

**16:9 横長は、Instagramフィードで最悪のアスペクト比である。**

| 形式 | Instagram フィードでの表示 |
|---|---|
| **1920×1080（現在）** | **画面幅の一部を占める細い帯。上下に大量の余白。指でスクロールすると一瞬で通過する。** |
| 1080×1350 (4:5) | 縦に大きく表示。フィードで最も面積を取る。 |
| 1080×1920 (9:16) | Storiesの全画面。 |

1週間かけて7人で作った作品が、フィード上では**親指1回で消える細い帯**として表示される。
**これだけで外側のバイラルループはほぼゼロになる。**

#### 問題2：カルーセル書き出しが、Rotashに全く見えない

```swift
static func photoURLs(for week: RotashWeek) -> [URL] {
    // 元の横長写真をそのまま書き出している
```

7分割で表示されているのは**アスペクトフィルで切り取られた細長い部分**だが、
カルーセルに書き出されるのは**元の16:9写真の全体**である。

つまりカルーセルで投稿されるのは、**7枚のバラバラな横長写真**であり、
そこにRotashらしさは1ミリも残っていない。**ただの写真7枚である。**

これでは「これ何？」は絶対に起きない。

#### 問題3：ブランド要素が完全にゼロ

- ロゴ・ワードマークなし
- 週の日付なし
- メンバー名なし
- URL・ハンドルなし

黒背景に写真が並んでいるだけの画像は、**誰が見てもRotashだと分からない。**
「これ何？」と聞ける手がかりが1つもない。

### E-3. 解決：作品をフィルムストリップとして定義する

**7分割が細長いこと** — PRODUCT_PHILOSOPHY 5, 21, 22 で「最大の弱点」とされている性質を、
**ブランドそのものに変える。**

> 7分割は「狭いコマ」ではない。**35mmフィルムの1本のストリップ**である。

細長いコマが横に並んだ帯は、**フィルムのコンタクトシートそのもの**である。
この見立てが成立すると、いくつもの問題が同時に解ける：

| 問題 | フィルムストリップ表現による解決 |
|---|---|
| コマが細長すぎる | **フィルムのコマは元々細長い。** 仕様ではなく様式になる |
| ブランド要素がない | フチ（rebate）に ROTASH / 日付 / コマ番号が入る — フィルムの実物がそうだから |
| モノクロ路線の根拠が弱い | フィルム＝モノクロが自然。既存のUI方針と完全に一致 |
| 「これ何？」が起きない | **フィルムストリップは説明不要で目を引く** |
| No Shot の黒枠が「欠け」に見える | 未露光のコマ。作品の一部として自然 |

**新しい共有画像の仕様（1080 × 1920 / 9:16 を第一形式とする）：**

```
┌───────────────┐  1080 × 1920 (9:16)
│ THIS WEEK     │  ← 画面が既に持っている見出し
│ 2026.08.31 —  │  ← 週の日付も既にある
│ ┌───────────┐ │
│ │MON  ▁▁▁▁▁ │ │  ← 7分割を「横帯 × 7」として縦に積む
│ ├───────────┤ │     （アプリの縦長スロットを90°展開した形）
│ │TUE  ▁▁▁▁▁ │ │
│ ├───────────┤ │
│ │WED  ▁▁▁▁▁ │ │
│ ├───────────┤ │
│ │THU        │ │
│ ├───────────┤ │
│ │FRI        │ │
│ ├───────────┤ │
│ │SAT        │ │
│ ├───────────┤ │
│ │SUN        │ │
│ └───────────┘ │
│ R O T A S H   │  ← 画面に**唯一足りない**もの
└───────────────┘
```

**設計原則：**

- **画面そのものを出す。** 見出し・週の日付・曜日・担当者名は、
  すでに `ThisWeekView` の構図の一部として存在している。
  **別の署名ブロックを下に足すと、完成された構図が壊れる**
- **足すのは `ROTASH` の1語だけ。**「THIS WEEK」は検索できない。固有名詞が要る
- **今日を示すアクセント線（`Palette.live`）は残す。** 進行中のシェアでは
  「これは今まさに起きている」という情報になる
- **1タップで完成する。** 選択肢・テンプレート・編集は出さない
  （`WorkShareButton` の confirmationDialog は2択あるが、1つに減らす）
- **写真そのものは加工しない**

**なぜ 9:16 縦を第一にするのか（4:5 ではなく）：**

理由は「Stories が主戦場だから」だけではない。**写真の写る量が根本的に違う。**

| | アプリの1枠 | 9:16 の1帯 |
|---|---|---|
| 形 | 246 × 784（**1 : 3.2 の縦長**） | 1080 × 246（**4.4 : 1 の横長**） |
| 16:9 の写真を aspectFill すると | 高さを合わせて左右を切る | 幅を合わせて上下を切る |
| **残る横幅** | **17.7%** | **100%** |
| 残る高さ | 100% | 40.4% |

**アプリは、撮った写真の横幅を 82% 捨てている。**

これは `PRODUCT_PHILOSOPHY.md` 5 / 21 / 22 で「最大の検証項目」とされてきた
「自撮り・顔・上半身に偏る」問題の、そのままの原因である。
横幅が 18% しか残らない枠では、風景も、机も、食事も、街も**構図として成立しない**。
残るのは顔だけだ。

**9:16 の横帯に組み直すと、写真の横幅が丸ごと残る。**
つまり共有画像は、**アプリが切り捨てている部分を初めて見せる場所**になる。

> アプリの7分割は**ファインダー**であり、9:16 の共有画像は**プリント**である。
> 同じ7枚だが、見えているものの量が違ってよい。

**4:5（フィード）版は当面つくらない。**

スマホは基本的に縦で見られていて、Stories / Shorts / TikTok が主戦場である以上、
横長に近い形式は**フィード上で小さく表示され、親指を止められない**。
9:16 を1つ作り切ることを優先し、フィード版が本当に要るかは後で判断する。

### タイトルは、この画像の上に載る

`M3` で入れる「7枚目を撮った人が付ける1行」は、**この共有画像に載る唯一の人間の声**である。
画面の他の要素（曜日・日付・担当者名）はすべてシステムが生成したものなので、
タイトルがないと、どれだけ作り込んでも**自動生成された広告に見える**。

そしてこれは、**アプリ内で唯一の「撮る以外の能動的な行為」**でもある。
現状 Rotash でユーザーがすることは週に1回シャッターを押すことだけで、
「自分たちが作った」という感覚を持てる場所が存在しない。

タイトルを付ける人は毎週変わる（日曜の担当は `AssignmentPlanner` が毎週組み替えるため、
明示的な仕組みを足さなくても自然に回る）。**特別感が1人に固定されない。**

### E-4. 「これ何？」を生む要素の設計

「これ何？」が起きるには、**見た人の中に説明されていない問いが残る**必要がある。

| 見た人の疑問 | それを生む要素 |
|---|---|
| 「なんで7枚？」 | 7という不自然な数と、MON〜SUN の曜日 |
| 「なんで細長い？」 | フィルムストリップ形式 |
| 「これ全部この人が撮ったの？」 | **7人の名前が併記されている** ← 最重要 |
| 「1週間分？」 | 週の日付範囲 |
| 「Rotashって何？」 | ワードマーク |

**最も強いのは「7人の名前」である。**

1枚の画像に7人の名前が載っていると、見た人は必ず考える：
**「これ、7人で作ったの？どうやって？」**

そして名前が載っていることには、副次効果がもう1つある。
**7人それぞれが、自分の名前が載った作品を持つ。**
だから7人全員が投稿する動機を持つ。1つの作品が最大7回投稿される。

### E-5. キャプションを提供しない

シェア時に定型キャプションを自動挿入したくなるが、**やらない。**

```
やってはいけない：
  「Rotashで友達と1週間の作品を作りました！ #Rotash」
  → 広告に見える。投稿者が恥ずかしい。誰も投稿しない。

正しい：
  キャプションは空。ユーザーが自分の言葉で書く。
  画像だけが Rotash を説明する。
```

**「Rotashを宣伝するために投稿する」状態を作ってはいけない。**
投稿の動機は「自分たちの1週間が良かったから」でなければならない。
画像が十分に強ければ、キャプションは要らない。

そしてこれが、BeRealが壊れた道筋を避ける道でもある。
BeRealは著名人・ブランドを入れた瞬間に「anti-Instagram」という前提を自分で壊した。
[（出典）](https://www.dazeddigital.com/life-culture/article/61166/1/why-did-bereal-fail-social-media-instagram-authenticity)
**Rotashにとっての同じ過ちは、作品をマーケティング素材として扱うことである。**

### E-6. プロフィール導線をどう作るか

「これ何？」の答えにたどり着く経路は、あえて**細く**する。

```
作品を見る → 「これ何？」 → 投稿者に直接聞く → 「Rotashってアプリ」
                                    ↑
                        ここが最良の導線。人が説明する。
```

画像内にURLやQRを大きく入れるのは逆効果である（広告になる）。
**ワードマーク "ROTASH" だけで十分。** 検索できる固有名詞があれば、経路は成立する。

そして**人づてに聞く経路のほうが、変換率が圧倒的に高い。**
なぜなら聞いた時点で、その人は既に「一緒にやる相手（＝グループの1人目）」だからである。

## F. 「待つ時間」を価値に変える

### F-1. 待ち時間は、Rotash唯一の防御可能な資産である

普通の写真アプリのループ：

```
撮る → 見る → 終了        （所要時間：30秒。1日1回で飽和する）
```

Rotashのループ：

```
待つ → 誰が撮る？ → どんな写真？ → 見る → 次は誰？ → 待つ
       ↑                                              │
       └──────────────────────────────────────────────┘
       （所要時間：7日間。ずっと未解決の問いが立っている）
```

**待ち時間が長いことは、コンテンツ量が少ないことの言い訳ではない。**
**待ち時間そのものが、他社が模倣できない唯一のコンテンツである。**

なぜ模倣できないか：
InstagramもBeRealも、**コンテンツ供給を増やす方向にしか進化できない**。
「今日は撮れません」を実装できるアプリは、コンテンツで戦っていないアプリだけである。

### F-2. 待ち時間を構成する2つの問い

Rotashの待ち時間には、**性質の違う2つの問い**が入っている。

```
朝                          夜
│                           │
├── 問い1：今日は誰？ ───────┤
│   （答えは朝すぐ出る）      │
│                           │
├────── 問い2：何を撮る？ ───┤
│   （答えは夜まで出ない）    │
▼                           ▼
```

**この2段構えが Rotash の日次ループの実体である。**

| | 問い1「今日は誰？」 | 問い2「何を撮った？」 |
|---|---|---|
| 答えが出るまで | 数秒（朝の通知） | 数時間〜1日 |
| 感情 | 意外性・不確実性 | 期待・好奇心 |
| 対象 | グループ全体 | 特定の1人 |
| 現状 | ○ 構造は実装済み（`revealedAssignee`） | **× 撮られたことが誰にも伝わらない** |

PRODUCT_PHILOSOPHY 4 が「最大の未解決問題」として挙げている
**「今日は誰？」から「何を撮った？」への接続**は、
**技術的には「撮られたことを知らせる手段がない」という一点に集約される。**

現在、同期はアプリを開いた時・撮った時・引っぱった時にしか走らない。
つまり**誰かが撮っても、他の6人がたまたまアプリを開くまで、誰も知らない。**

問い2の答えが出たことを誰も知らないので、問い2は問いとして成立していない。

### F-3. 通知設計 — 2種類、1日最大2通

通知は必要である。しかし**依存性を高める設計にはしない。**
判定基準を1つ置く：

> **その通知は「友達について」か、「アプリについて」か。**
> 友達についての通知だけを送る。

| # | タイミング | 文面 | 宛先 | 頻度 |
|---|---|---|---|---|
| 1 | **朝 8:00** | 「今日は MINA」 | 全員 | 1日1通 |
| 2 | **撮影された時** | 「MINA が撮った」 | 撮った本人以外 | 1日最大1通 |

**これ以外は送らない。** 合計 1日最大2通、週14通。

なぜこれで足りるか：

- 通知1が **日次の起点**を作る（毎朝8時にRotashのことを思い出す = 習慣の錨）
- 通知2が **問い2の解決**を知らせる（「何を撮った？」の答えが出た）
- 通知1と通知2の間に、**数時間の待ち時間が挟まる** — これが体験の本体

**送ってはいけない通知（DON'T）:**

| 通知 | なぜダメか |
|---|---|
| 「今日はあなたの番です！まだ撮っていません」（催促・複数回） | **義務化の入口。** Rotashが「やらなきゃいけないこと」になる |
| 「あと2枚で完成！」 | 進捗の煽り。作品を作業に変える |
| 「3日間開いていません」 | アプリについての通知。友達についてではない |
| 「◯◯さんも見ています」 | 監視。気持ち悪い |

**担当者本人への催促は、当日1回だけ**許容する（夜20:00、まだ撮っていない場合のみ）。
これは催促ではなく**「今日で終わってしまう」というリマインド**であり、
No Shot が「忘れていた」で起きるのを防ぐ。それ以上は送らない。

### F-4. 通知1を「朝8時固定」にする理由

深夜0時に日付が変わった瞬間に担当者が確定するのではなく、
**朝8時に全員へ同時に知らせる。**

これによって「Rotashの1日は朝8時に始まる」という**共有された時刻**ができる。

Wordleが「1日1問・全員同じ問題」で機能したのも、
BeRealが「全員同時に通知」で機能したのも、
**個人の都合ではなく、全員で共有された時間軸を持っていたから**である。

Rotashは「同じ瞬間を共有しない」ことを差別化としている（PRODUCT_PHILOSOPHY 2）。
**それは撮影の話であって、通知の話ではない。**
撮影は非同期でよいが、**朝の合図だけは同期させる。**

7人が別々の場所で、同じ朝8時に、同じ名前を見る。
そこから7人がそれぞれ別の1日を過ごし、そのうち1人だけが1枚を残す。
**これがRotashの1日の形である。**

### F-5. 待ち時間中に「機能」を足さない

待ち時間を埋めようとして、以下を追加したくなる。**全部やらない。**

- 「今日の撮影ヒント」 — お題を出した瞬間に、日常ではなく課題になる
- 「他のグループの作品を見る」 — タイムラインの入口。J参照
- 「メンバーとチャット」 — LINEで既にやっている。Rotashが持つ理由がない
- 「今日の写真を予想する」 — ゲーム化。7分割の作品性を薄める

**待ち時間は埋めるものではない。**
待ち時間が空いているからこそ、夜に写真が来たときの反応が大きくなる。

## G. Retention の分解と離脱点の特定

### G-1. 4段階の分析

#### Day 1 — 「面白そう」

| 項目 | 内容 |
|---|---|
| 感情 | 好奇心。「7分割って何だ」 |
| 行動 | 作成 or 参加 → 招待コードを見る → 横にする → 7分割を見る |
| UX | ○ 横にした瞬間に7分割が現れる体験は強い。縦で見せない判断は正しい |
| 通知 | なし |
| ソーシャル | **ここが全て。人が集まるかどうかだけが問題** |
| 報酬 | 「なんか良さそう」という感覚のみ。まだ何も起きていない |
| **不安** | **誰も入らない。1人グループのまま「今日は自分」が7日続く** |

#### Day 2〜6 — 「今日は誰が撮るんだろう？」

| 項目 | 内容 |
|---|---|
| 感情 | 期待 → 好奇心 → 満足（他人の写真を見る） |
| 行動 | 朝：今日の担当を確認 / 夜：追加された写真を見る |
| UX | ○ 見るのに制限がない設計は正しい（全員がいつでも全部見られる） |
| 通知 | **× 存在しない。開くきっかけがゼロ** |
| ソーシャル | 6日間、自分は観客。他人の1日を見ることが体験の中心 |
| 報酬 | 1枠増える。作品が完成に近づく |
| **不安** | **開く理由がないので開かない。開かないので写真が増えたことにも気づかない** |

#### Day 7 — 「完成した！」

| 項目 | 内容 |
|---|---|
| 感情 | 達成感。7人で1つを作り終えた感覚 |
| 行動 | 完成した作品を見る → （本来は）シェアする |
| UX | **× 完成の演出がない。縦画面にテキスト1行が出るだけ** |
| 通知 | **× 完成しても誰も知らない** |
| ソーシャル | **7人が同時に「終わった」と感じるべき瞬間。今は誰も同時に感じていない** |
| 報酬 | 作品。Memories に1本 |
| **不安** | **完成に気づかないまま月曜が来て、作品が静かに Memories へ消える** |

#### Week 2 — 「もう一回やろう」

| 項目 | 内容 |
|---|---|
| 感情 | ○ 決断が要らない。月曜が来ただけ |
| 行動 | 朝、新しい担当を見る |
| UX | ○ `rollWeekIfNeeded()` が自動で処理。**この設計は正しい。守る** |
| 通知 | × なし（朝8時通知があれば解決する） |
| ソーシャル | 同じ7人。人間関係が既に資産になっている |
| 報酬 | Memories が積み上がる |
| 不安 | 1人抜けると穴が空く。ただし No Shot 設計により作品は壊れない（○） |

### G-2. 離脱点のランキング

**離脱の大きさ × 起きる確率 × 気づきにくさ**で並べる。

| 順位 | 離脱点 | 何が起きるか | 損失 |
|---|---|---|---|
| **1** | **Day 0-1：招待が刺さらない** | 6桁コードだけ送られて「何それ」で終わる。グループが1〜2人のまま | **ループが1周も回らない。全損。しかも静かに起きる** |
| **2** | **Day 7：完成が外に出ない** | 完成に気づかず、シェアされない | **バイラル係数がゼロになる。既存ユーザーは残るが成長しない** |
| **3** | **Day 2-6：開くきっかけがない** | 通知がないので忘れる | 日次リテンションが崩壊。完成率も下がる |
| 4 | Day 2-6：写真が単調 | 全員自撮り → 「1週間」に見えない | 完成しても感動がない → シェアされない（2と複合して効く） |
| 5 | Day 1：参加直後の空白 | 木曜参加で担当が日曜だと3日間何もない | 単発の離脱。写真が既にあれば緩和される |

**1位と2位が構造的に致命的である。**

- **1位はAcquisition/Activationを殺す**（入口が閉じている）
- **2位はViralを殺す**（出口が閉じている）

つまり現在のRotashは、**中身（Day 2-7の体験）はよく設計されているのに、
入口と出口の両方が塞がった箱**になっている。

**そして最も注意すべきは、両方とも「静かに起きる」ことである。**
エラーも出ないし、クラッシュもしない。データ上は「グループが作られたが継続しなかった」
としか見えない。原因が「体験がつまらない」に誤診されるリスクが高い。

**→ 施策の優先順位は、Retention施策より先に、入口（招待）と出口（シェア）である。**

## H. 競合・成功事例からの構造抽出

各プロダクトについて「なぜ翌日も戻るのか」の**構造**だけを抽出する。
機能のコピーは一切しない。

### H-1. BeReal — 同期性は強いが、同期性だけでは持たない

**なぜ機能したか：** 全員に同時に通知が飛ぶ。2分の制限時間。撮らないと他人のを見られない。
**「今この瞬間、全員が同じことをしている」**という強制的な同期が、毎日の予定を作った。

**なぜ失速したか：** ピーク時7,300万から2023年3月には3,300万へ。
2024年のダウンロードは前年比60%減。2024年にVoodooへ5億ユーロで売却。
[（出典1）](https://www.businessofapps.com/data/bereal-statistics/)
[（出典2）](https://www.socialmediatoday.com/news/bereal-struggling-users-running-out-of-funding/710400/)

失速の主因は**著名人・ブランドの導入**である。
「anti-Instagram」であることが唯一の価値だったのに、自分でそれを壊した。
[（出典）](https://www.dazeddigital.com/life-culture/article/61166/1/why-did-bereal-fail-social-media-instagram-authenticity)

**構造的な弱点はもう1つある。BeRealには蓄積がない。**
毎日リセットされ、昨日の投稿には意味がない。
だから**「やめても失うものがない」**。習慣が切れた瞬間に完全に切れる。

**Rotashへの示唆：**
- 同期性は「朝8時の通知」だけに限定して借りる（F-4）
- **蓄積（Memories の積層）はBeRealが持たなかった防御壁である。ここで差がつく**
- 外部の有名人・ブランドを入れる道は、BeRealの死因そのもの。**永久に禁止**

### H-2. Locket — 上限があるから価値がある

**なぜ機能したか：** ホーム画面ウィジェットに親しい友達の写真が直接出る。
**アプリを開く必要すらない。** 8,000万DL、DAU 900万超。
[（出典）](https://apps.apple.com/us/app/locket-widget/id1600525061)

**最も重要な構造は「20人まで」という上限である。**
上限があることで、Locketに入れる相手は**選ばれた relationship** になる。
フォロワー数で競う世界の対極に、**明示的な希少性**を置いた。

**Rotashへの示唆：**
- **7人という数字を「定員」として使う根拠がここにある（0-2）**
- 「7枠のうち1つ」は、Locketの「20人のうち1人」と同じ心理を、より強く作れる
  （7は20より圧倒的に希少）

### H-3. Wordle — 成長したのは共有形式であって、ゲームではない

**なぜ機能したか：** 1日1問。全員同じ問題。追いつけない（昨日の問題は解けない）。
2分で終わる。

**なぜ爆発したか：** 絵文字グリッド共有の追加後、2ヶ月で90人→300万人。
[（出典）](https://slate.com/culture/2022/01/wordle-game-creator-wardle-twitter-scores-strategy-stats.html)

グリッドの3条件：**一目でそれと分かる / 答えを明かさない / 説明が要らない**（E-1）。

**Rotashへの示唆：**
- **これが Rotash にとって最も重要な事例である**
- 7分割は「一目でそれと分かる」を既に満たしている。**あと2つを満たせば同じことが起きうる**
- 「答えを明かさない」の Rotash 版 = **完成品を見ても、どうやって作ったか分からない**。
  7人の名前を載せることで「7人でどうやって1枚を？」という問いが残る
- **開発すべきは機能ではなく共有形式である**

### H-4. Duolingo — streak は強力だが、Rotashでは使えない

**なぜ機能したか：** streak が日次リテンションを2倍にする。
2025年Q3でDAU 5,000万超、前年比36%増。
**フレンドストリークを持つユーザーは、日次レッスン完了率が22%高い。**
[（出典1）](https://duolingo.deconstructoroffun.com/mechanics/streaks)
[（出典2）](https://trophy.so/blog/duolingo-gamification-case-study)

**注目すべきは「フレンドストリーク」のほうである。**
ランキングで他人に勝つ動機より、**「特定の1人をがっかりさせたくない」**動機のほうが強い。
順位は数字だが、フレンドストリークは関係である。

**Rotashへの示唆：**
- **個人のstreakは実装しない**（C-1の通り、7人依存で毎週30%壊れる）
- しかし「特定の人をがっかりさせたくない」という力は、
  **Rotashでは既に構造として存在している**：
  **自分が撮らないと、7分割に黒い穴が空き、それを6人が見る。**
  数字を1つも足さずに、Duolingoのフレンドストリークと同じ力が働いている
- **だからこそ No Shot を「失敗」として演出してはいけない**（現在の `—` だけの表示は正しい）。
  作品に穴が残るという事実だけで十分に効いている。それ以上責めると義務になる

### H-5. Snapchat — 「消える」が生む、追いつけなさ

**なぜ機能したか：** 消えるから今見る。ストリークが関係の指標になる。

**Rotashへの示唆：**
- Rotashは逆に「残る」で戦う。**消えるものはBeRealが取った席。埋まっている**
- ただし「追いつけなさ」の原理は借りる：
  **過ぎた日は No Shot として確定し、後から埋められない**（`allowCatchUpShooting = false`）。
  この設計は正しい。**後から埋められるようにした瞬間、待ち時間の価値が消える**

### H-6. Pokémon GO — 一緒にいる理由を作った

**なぜ機能したか：** レイドは1人ではクリアできない。**アプリが人を物理的に集めた。**

**Rotashへの示唆：**
- 「1人ではクリアできない」という構造は Rotash と同じ
- **ただしRotashは、集まらなくていい。** ここが決定的に優れている
- Pokémon GOのレイドは同じ場所・同じ時間を要求するため参加コストが高い。
  **Rotashは「同じ1週間」だけを要求する。参加コストが桁違いに低い**
- **これが Rotash の最大の構造的優位である。**
  離れていても、時差があっても、生活リズムが違っても、同じ作品を作れる

### H-7. 横断して見えること

| プロダクト | 戻る理由 | 巻き込む理由 | 長期利用の理由 | 弱点 |
|---|---|---|---|---|
| BeReal | 同時通知 | 友達がいないと空 | **なし（蓄積ゼロ）** | 蓄積がない |
| Locket | ウィジェット常在 | 上限20の希少性 | 関係が濃い | 蓄積が薄い |
| Wordle | 1日1問・追いつけない | **共有グリッド** | 記録・習慣 | 社会性が弱い |
| Duolingo | streak・関係 | フレンドストリーク | 学習の蓄積 | 義務化しやすい |
| Snapchat | 消える・streak | 相互性 | 関係の指標 | 義務化 |
| Pokémon GO | 位置・イベント | 1人でクリア不可 | コレクション | 参加コスト高 |
| **Rotash** | **今日は誰？** | **7枠の空き** | **Memoriesの積層** | **入口と出口が塞がっている** |

**Rotashの列だけ、3つの理由が全部違う軸から来ている。**
戻る理由は不確実性、巻き込む理由は希少性、長期利用の理由は蓄積。
どれか1つが弱っても他が支える。これは他社にない構造である。

**弱点は体験そのものではなく、接続部にある。** そこだけを直せばいい。

## I. 追加すべき機能の評価

各候補を6軸で評価する。**◎○△×** の4段階。

| 機能 | Growth | Retention | Viral | UX複雑化 | 実装コスト | 世界観 | 判定 |
|---|---|---|---|---|---|---|---|

### I-1〜I-5. MUST 5項目の詳細

#### I-1. 招待リンク + 未完成作品の画像

**なぜ最優先か：** ループが1周も回らない原因の第1位（G-2）を直接潰す。

必要な実装：
- `Info.plist` に `CFBundleURLTypes`（`rotash://join/{CODE}`）を追加
  — 現在は `.rotash` ファイルのUTIしか定義されていない
- 招待共有時に「現在の週の7分割画像 + テキスト + リンク」を `UIActivityViewController` に渡す
- 空き枠を含んだ画像を生成（`WorkExporter.contactSheetURL` を空枠込みで拡張）
- リンクから起動したら、コード入力をスキップして名前入力だけにする

**世界観との整合：◎** 招待画面が「招待画面」ではなく「作品の状態」になる。
Rotashの思想（作品が中心）と完全に一致する。

#### I-2. ブランド化されたシェア画像

**なぜ最優先か：** ループの出口（G-2 第2位）を直接潰す。E-3 の仕様で実装する。

必要な実装：
- `WorkExporter.contactSheetURL` を 1080×1350（4:5）と 1080×1920（9:16）に作り直す
- フチにワードマーク / 週の日付 / 曜日 / メンバー名を描画
- **`WorkShareButton` の選択肢を2つから1つに減らす**
  （「7枚を書き出す」は、Rotashに見えない画像を配ってしまうので廃止か、隠す）

**UX複雑化：むしろ減る。** 現在の confirmationDialog（2択）が1タップになる。

#### I-3. 通知2種

**なぜ必要か：** 日次ループを支える唯一の手段（F-3）。

実装上の注意：
- 現在プッシュ通知の基盤が一切ない（`aps-environment` なし、APNs未設定）
- **ただし通知1（朝8時の担当発表）はローカル通知で実装できる。**
  担当者は週の開始時点で内部的に決まっているため、
  **7日分のローカル通知を週の開始時に予約するだけでよい。** サーバー不要
- 通知2（撮られた）はプッシュが必要。**先に通知1だけ実装する**のが正しい順序
  （コストが小さく、効果の大半を取れる）

#### I-4. 完成の瞬間

**なぜ必要か：** バイラルの起点（B-2）。実装コストが最小で効果が最大。

必要な実装：
- 週の全枠が決着（`isFinished`）した瞬間を検出
- 完成画面（進行中とは違う見え方 — 余白 + 週の日付 + メンバー名）
- そこから直接 SHARE
- **「来週も続ける？」は置かない**（B-3）

#### I-5. 人数を cap として扱う

**なぜ必要か：** 0-1 の最悪シナリオを潰す。

必要な実装：
- 定員7で `addMember` / 参加を制限
- 縦画面に `MEMBERS 3 / 7` と空き枠 `—` を表示（文言なし・タップで招待）
- 1〜2人のときは「今日の担当」を出さない（D-4）
- **撮影は禁止しない**

### I-6. 「Next Rotash」を作ってはいけない理由

候補として挙げられている「Next Rotash」は、**明確に DON'T である。**

「次のRotashを始める」というボタンが存在すると：

- 週が「終わる」ものになる（今は終わらない。ただ次の週になる）
- 継続が**能動的な決断**になる（B-3の通り、決断は継続率を下げる）
- 7人全員が押す必要が生まれる（0.9^7 = 48%）
- 押さなかった週が「途切れた週」になる

**現在の自動週送りのほうが、あらゆる面で優れている。**
「Next Rotash」は、既に正しく解けている問題に、悪い解を上書きする機能である。

## K. North Star Metric

### K-1. 選定

**North Star Metric：**

> ## 今週、作品を完成させたグループ数
> **WCG — Weekly Completing Groups**
>
> 定義：3人以上のメンバーを持つグループのうち、その週が `isFinished` に到達し、
> かつ写真が入った枠が全枠の半数以上あるグループの数

**なぜこの1つか：**

| 条件 | WCG がそれを満たす理由 |
|---|---|
| **単位が正しい** | Rotashの価値の最小単位は「ユーザー」ではなく「グループ」。1人のDAUは何も意味しない |
| **全工程を通過しないとカウントされない** | グループ作成（Acquisition）→ 3人以上集まる（Activation）→ 7日間撮り続ける（Engagement）→ 日曜に到達（Completion）。**どこか1つでも欠けたら数えられない** |
| **増え方が2つしかない** | 既存グループが継続する（習慣）か、新しいグループが生まれる（バイラル）か。**求めているものと完全に一致** |
| **不正に強い** | 通知の乱発でも、1人のヘビーユーザーでも増えない。7人が7日間動かないと増えない |
| **比率ではない** | 「完成率」だと、悪いグループが離脱するだけで数字が上がってしまう。**実数だから誤魔化せない** |

DAU / MAU では、1人グループが毎日開いていても数字が上がる。
**それはRotashが機能していない状態そのものである。** WCG はゼロのままになる。

### K-2. 成長方程式

WCG は次の式で動く。**これがRotashの事業の全てである。**

```
WCG(来週) = WCG(今週) × ( R + K )

  R = 週次継続率
      今週完成したグループのうち、来週も完成する割合

  K = 作品あたりのグループ生成数
      完成作品1つから生まれ、実際に完成まで到達する新規グループの数

  成長条件：  R + K > 1
```

**この不等式が、Rotashのすべての意思決定の判定基準になる。**

> **補正（重要）：** この式は `WCG(今週) = 0` のとき永久に 0 のままである。
> リリース直後は右辺の第1項がゼロなので、手で立ち上げるグループ数 `S(t)` を足した
> `WCG(t+1) = WCG(t) × (R + K) + S(t)` が正しい。
> Phase 0 では **S がすべて**であり、`R + K` はまだ測る母数すらない。
> 詳細は [`GO_TO_MARKET.md`](GO_TO_MARKET.md)。

具体例：

```
今週 100グループが完成した

ケース1（現状の推定）
  R = 0.5  （完成の演出がなく、通知もないので継続しない）
  K = 0.05 （シェア画像が魅力的でないので、ほぼ拡散しない）
  → 来週 55グループ。R + K = 0.55 < 1 → 縮小する

ケース2（MUST 5項目の実装後）
  R = 0.7  （通知＋完成の儀式＋Memoriesの積層）
  K = 0.4  （ブランド化されたシェア + 招待リンク）
  → 来週 110グループ。R + K = 1.1 > 1 → 成長する
```

**Rが0.7でも、Kが0.3を超えないと成長しない。**
**つまり「シェア」は「あったらいい機能」ではなく、成長の必要条件である。**

これが、セクションE（完成作品をGrowth Engineにする）が
Retention施策より優先される数学的な理由である。

### K-3. 補助指標（サブメトリクス）

WCG は結果指標なので、動かすためのレバーを4つ持つ。

| # | 指標 | 定義 | 何を診断するか | 目標の目安 |
|---|---|---|---|---|
| 1 | **3人到達率** | 作成されたグループのうち、7日以内に3人以上になった割合 | **入口が開いているか**（G-2 第1位） | 60%以上 |
| 2 | **完成率** | 3人以上のグループのうち、週を完成させた割合 | 日次ループが回っているか | 70%以上 |
| 3 | **R（週次継続率）** | 完成したグループが翌週も完成する割合 | 習慣になっているか | 70%以上 |
| 4 | **K（作品あたり新規グループ数）** | 完成作品1つから生まれ完成まで至った新規グループ数 | **出口が開いているか**（G-2 第2位） | 0.3以上 |

**Kの計測方法：** 招待リンクに発行元グループIDを埋め込み、
そこから作られた新規グループを紐づける。
**I-1（招待リンク）を実装しないと、Kは原理的に測定できない。**
これもI-1が最優先である理由の1つ。

### K-4. 見てはいけない指標

以下は**改善しようとした瞬間にプロダクトを壊す**ので、KPIにしない。

| 指標 | なぜ危険か |
|---|---|
| DAU / セッション時間 | 増やす最短手段は通知の乱発。義務化への直行便 |
| 1日あたり撮影枚数 | Rotashは1日1枚。増えることは仕様違反 |
| アプリ内滞在時間 | 待ち時間が本体。滞在時間が短いのは正しい状態 |
| ダウンロード数 | 3人集まらないDLは価値ゼロ。**BeRealの失速もDLではなく継続で起きた** |
| 総ユーザー数 | 1人グループの100人より、7人グループの7人のほうが価値が高い |

## L. 最終戦略

### L-1. MUST — 絶対にやる

**判定基準：これがないとループが1周も回らない。**

| # | 施策 | 直す穴 | 効く指標 |
|---|---|---|---|
| **M1** | **招待をリンク + 未完成作品の画像にする**<br>（URL Scheme、共有時に7分割画像を添付、リンクから起動時はコード入力をスキップ） | 入口（G-2 第1位） | 3人到達率、K |
| **M2** | **共有画像を 9:16 で、画面そのものとして出す**<br><span style="color:var(--dim)">1080×1920。7分割を「横帯 × 7」に組み直して縦に積む。見出し・日付・曜日・担当者名は画面が既に持っているので足さない。**足すのは `ROTASH` の1語だけ**。写真の横幅が 18% → 100% になる（E-3）</span> | 出口（G-2 第2位） | **K** |
| **M3** | **完成の瞬間を作る + 最後の1人がタイトルをつける**<br>（`isFinished` を検出 → 通知1通 → 完成形 → **7枚目を撮った人が1行だけタイトルを入れる** → SHARE。「来週も続ける？」は置かない） | 出口 | K、R |
| **M4** | **朝8時のローカル通知「今日は◯◯」**<br>（週の開始時に7日分予約するだけ。サーバー不要） | 日次ループ | 完成率、R |
| **M5** | **人数を cap として扱う**<br>（定員7、`MEMBERS 3 / 7` と空き枠 `—` を文言なしで表示、1〜2人では「今日の担当」を出さない、撮影は禁止しない） | 入口・体験の成立 | 3人到達率、完成率 |

**M1 → M2 → M3 → M4 → M5 の順で実装する。**
入口（M1）と出口（M2, M3）が先。日次の改善（M4）はその後。
**理由：入口と出口が塞がったままRetentionを改善しても、K + R が 1 を超えない。**

### 追補：M1 と M2 は1つの作業に統合する

M1（招待画像）と M2（シェア画像）を別々の施策として並べたが、**分ける必要はない。**

Rotash の作品は月曜から日曜まで毎日違う姿をしていて、そのどれもがシェアできる。
**同じ画像生成器が、0/7 では招待状になり、3/7 では「これ何？」になり、7/7 では作品になる。**

```
        1つの生成器（4:5 / 9:16・フチにワードマーク・週・曜日・メンバー名）
              ↓            ↓             ↓
        0/7 → 招待状   3/7 → 途中経過   7/7 → 作品
```

変わるのは「何枚埋まっているか」と `n / 7` の数字だけ。**実装量が減り、効果が増える。**

そして **3/7 は 7/7 より強い**。完成品は答えであり、未完成品は問いだからである
（Wordle のグリッドが「答えを明かさない」ことで機能したのと同じ構造）。

シェア機会も 1週1回から**最大6回**に増える。最も効くタイミングは**撮った直後** —
自分の1枚が7分割に入った瞬間が、その週で最も見せたい瞬間だからだ。
ただし撮影後に共有シートを自動で開くのは**禁止**（「即確定・確認画面なし」を壊す）。
7分割画面に静かに存在するだけでいい。

詳細は [`GO_TO_MARKET.md`](GO_TO_MARKET.md) 4章。

| L1 | **撮影画角の分離**（撮影は広く、7分割の表示は狭いまま） | 「7枚が自撮りばかりになる」がユーザーテストで確認された場合のみ。**PRODUCT_PHILOSOPHY 5, 21, 22 の検証結果次第**。これが真なら優先度はMUSTに繰り上がる |
| L2 | **複数グループ（上限3）** | 単一グループでR > 0.6 が確認できてから。それ以前にやると1つも濃くならない |
| L3 | 2秒動画 | 写真での体験が成立してから（PRODUCT_PHILOSOPHY 24 の優先順位に従う） |
| L4 | Memories の作品数に応じた表現の変化 | グループが10週続く事例が出てから |

### L-4. DON'T — やらない

- **セクションJ の全項目**（特に J-1 の10項目）
- **撮影カメラの全画面化** — 撮る人が前の6日分を横に並べたまま構図を決める構造が壊れる（`ThisWeekView` はライブビューを担当枠の中だけに出している）。「前日の写真に返す」連鎖は既にこの1点で成立しており、リアクション機能で代替してはいけない
- **シェアへの報酬（ポイント・特典）** — シェアが作業になり、シェア画像が広告として受け取られる
- **連続週数（streak）**
- **「Next Rotash」ボタン**
- **未来の担当表の公開**
- **完成作品への外部リアクション**
- **定型キャプションの自動挿入**
- **「7人集まるまで開始できない」ゲート**

### L-6. Rotashの定義

> ## 他のどの写真アプリも「自分が撮った1枚」を残すが、
> ## Rotashだけが「自分ひとりでは絶対に作れなかった1週間」を残す。

写真アプリの価値は、突き詰めれば「自分が見た良い景色を保存すること」である。
その軸で戦う限り、Rotashはカメラアプリにもフィルターアプリにも勝てない。

Rotashが唯一勝てる軸は、**「1人では成立しない」ことそのもの**である。

7枚のうち6枚は、自分が見ていない景色である。
その6枚は、6人の友達がその日に世界のどこかにいた証拠であり、
**同じ1週間を、離れた場所で、確かに一緒に生きた記録**である。

これは、どれだけ高性能なカメラでも、どれだけ賢いAIでも作れない。
**7人の1週間がなければ、絶対に存在しない画像だからである。**

## 付録：この資料の結論を3行で

1. **Rotashの体験（Day 2〜7）はよく設計されている。壊れているのは入口（招待）と出口（シェア）だけである。**
2. **「7人」は下限ではなく定員として設計する。下限はグループを殺し、定員はグループを特別にする。**
3. **成長条件は `R + K > 1`。Kを上げる唯一の手段は、完成作品そのものを、説明不要で「これ何？」を生む1枚にすることである。**
