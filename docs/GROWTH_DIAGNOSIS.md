## 2. 診断 — これは成長の問題ではない

### 2-1. 問いの立て直し

```
問い（依頼のまま）      「ユーザー数を増やすには？」
                              ↓
現状                    ユーザーがいない。プロダクトは生後7日。
                        ループを支える部品（通知・リンク・共有画像・計測）が
                        1つも実装されていない。
                              ↓
正しい問い              「Rotash のループは、そもそも物理的に1周できるのか？
                         できるとして、7人が1週間続けたくなる中身があるのか？」
```

**これは Growth の問題ではなく、Pre-Product-Market-Fit の問題である。**

PMF 前に成長施策を打つと、次の2つが同時に起きる。

1. 獲得したユーザーが体験に到達せず離脱する（費用が消える）
2. **その離脱が「プロダクトがつまらない」という誤ったシグナルとして記録される**

2 のほうが致命的である。`GO_TO_MARKET.md` 1章で「ゼロ週目の広告はマイナス」と
書いたのはこの意味であり、これは Rotash に固有の話ではなく PMF 前の一般原則でもある。

### 2-2. ただし、構造的なポジションは強い

診断が「早すぎる」で終わると誤解を生むので、公平に書く。

Rotash には、写真アプリでは稀な**構造的優位**が1つある。

> **1人では作品が完成しない。**

これは Instagram にも Locket にも BeReal にも真似できない。
なぜなら、あの3つは**1人で完結することが価値**だからである。
真似した瞬間に自分たちのコア（気軽さ・即時性）を壊す。

つまり Rotash は、**大手が構造的に追随できない領域**に立っている。
問題は、その優位が**まだ1行も実装されていない**ことである
（`GROWTH_STRATEGY.md` 0-1：1人でも7枚を完成できてしまう）。

**結論：思想は強い。ループは未実装。コアは未検証。**

## 3. 成長方程式と、律速変数

既存資料で導いた式を再掲する（導出は `GO_TO_MARKET.md` 0章）。

```
WCG(t+1) = WCG(t) × ( R + K ) + S(t)

  WCG = その週に作品を完成させたグループ数（North Star）
  R   = 週次継続率        K = 作品あたり新規グループ数
  S   = 人力で立てたグループ数
```

現在の各変数の状態を、事実に照らして評価する。

| 変数 | 現状 | 律速か |
|---|---|---|
| **S** | **0**。招待がコード手配りで、リンクも説明も無い | **律速** |
| **R** | 測定不能。週送りは自動なので構造は良いが、通知が無く開くきっかけがゼロ | 律速（ただし S の後） |
| **K** | **ほぼ 0**。共有物が 16:9 でブランド要素なし、カルーセルは Rotash に見えない | **律速** |
| 完成率 | 測定不能。1人グループを許すため、そもそも体験が成立しない場合がある | 律速 |

### 最も成長を制限している変数

**S でも K でもなく、その手前にある。**

```
S を増やそうとしても → 招待リンクが無いので配れない
K を増やそうとしても → 共有画像が Rotash に見えない
R を測ろうとしても   → 計測が1行も無い
完成率を上げようとしても → 通知が無く、開くきっかけが存在しない
```

> **律速変数は「ループを構成する部品が実装されていないこと」そのものである。**

これは戦略の問題ではなく、**実装の問題**である。
だから今後90日でやるべきことは、マーケティングではなく
`GROWTH_STRATEGY.md` の **MUST 5項目（M1〜M5）** を作り切ることになる。

## 4. 12のループ分類

依頼にあった12種類のループを、Rotash について分類する。

### 既に存在し、強い

| ループ | 状態 | コメント |
|---|---|---|
| **Collaboration Loop** | **強い（コア）** | 1人では完成しない。これが Rotash の全て。ただし現在コード上で強制されていない |
| **Social Loop** | 構造は強い / 動いていない | 「今日は誰？」は `revealedAssignee` で正しく実装済み。だが通知が無く発火しない |

### 存在するが弱い、または壊れている

| ループ | 状態 | 壊れている理由 |
|---|---|---|
| **Invitation Loop** | 壊れている | 6桁コードを手で配る。受け手に何のアプリか伝わらない |
| **Viral Loop** | ほぼゼロ | 共有画像にブランド要素なし。カルーセルは Rotash に見えない |
| **UGC Loop** | 内向き | 写真は生成されるがアプリの外に出ない |
| **Habit Loop** | 半分 | 自動週送りは正しい。朝の合図が無い |
| **Content Loop** | 未接続 | 20グループ×7日で140本作れるが、出す先の設計が無い |

### 潜在的に作れる

| ループ | 作り方 |
|---|---|
| **Identity Loop** | 「この7人」への所属感。タイトル（M3）と Memories の積層が最初の一歩 |
| **FOMO Loop** | **穏やかにのみ**。撮らなければ黒い穴が残り6人が見る、で既に十分。これ以上強めない |

### 作るべきではない

| ループ | 理由 |
|---|---|
| **Community Loop**（グループ横断） | 実装した瞬間にタイムラインになる。「自分たちの1週間」が「他人のコンテンツ」に置き換わる |
| **Network Effect**（グループ間） | 同上。ネットワーク効果は**グループ内で完結**させる。グループ同士をつなぐ価値は Rotash には無い |
| **Utility Loop** | Rotash は道具ではない。便利さで戦うとカメラアプリに負ける |

**Rotash の特異性はここにある。** 普通のサービスは Network Effect を最大化するが、
**Rotash は Network Effect を意図的に7人で打ち止めにする。**
7人を超えたつながりは、価値ではなくノイズになる。

## 5. 価値の分解

依頼にあった5分類で、Rotash の価値を評価する。

| 価値 | 強さ | 内容 |
|---|---|---|
| **Functional**（機能） | **弱い** | 写真を撮る・保存する道具としては、標準カメラに全面的に劣る |
| **Social**（社会的） | 強い | 7人で1つを作る。参加していないと話に入れない |
| **Emotional**（感情） | 中〜強 | 待つ・期待する・完成する |
| **Identity**（自己表現） | 潜在 | 「この7人」という所属。まだ表現手段が無い |
| **Network**（つながり） | **最強** | **1人では成立しない。これが唯一の防御可能な資産** |

### ここから直接導かれる、実務上の結論

> **Rotash は Functional Value が最も弱く、Network Value が最も強い。**

だから **Functional な言葉で宣伝すると必ず失敗する。**

```
✕  「友達と写真を撮れるアプリ」      → Functional。標準カメラで足りる
✕  「共同アルバムが作れます」        → Functional。Google フォトで足りる
⭕  「友達7人で1週間、1日1枚ずつ撮った」 → Network。1人では絶対にできない
```

`GO_TO_MARKET.md` 7章の投稿の型が正しい理由は、感覚ではなくこの分解にある。

そして **Identity Value が「潜在」で止まっている**ことが、
タイトル（M3）と Memories の積層を早く作るべき理由である。
この2つが、いま唯一「この7人」を表現できる場所になる。

## 6. 成長仮説 — 5つ

検証可能な形で立てる。**n=20 では A/B テストは成立しない**ので、
検証方法は「観察 + ファネル実数 + インタビュー」を基本とする。
統計的検定ができるふりをしない。

### 仮説1 — 入口（S）

> 予定を控えた言い出しっぺは「7人で1週間撮る」に価値を感じる。
> しかし6桁コードを手で配る必要があり、受け手に何のアプリか伝わらないため、
> **3人に到達しない。**

- **正しければ** 招待をリンク＋未完成作品画像にすると 3人到達率が上がる
- **検証** 全20グループを新方式で走らせ、Firestore の `members.count` 分布を見る。同時に「招待を送ってから最初の参加までの経過時間」を測る
- **成功** 3人到達率 **60%以上** / 招待から初参加まで **24時間以内が過半**
- **失敗** 40%未満 → 招待の問題ではなく**そもそも誘う動機が無い**。仮説を根本から見直す

### 仮説2 — 日次ループ（完成率）

> 参加者は担当日以外は撮れないが「今日は誰？」への好奇心で開く。
> しかし通知が無いため開くきっかけが存在せず、写真の追加にも気づかない。

- **正しければ** 朝8時のローカル通知だけで完成率が上がる
- **検証** `capturedAt` の時刻分布（通知後に撮影が集中するか）と週あたり充填数
- **成功** 完成率 **70%以上** / 担当日当日の撮影率 **80%以上**
- **失敗** 通知後も撮影が増えない → 問題は想起ではなく**撮る対象が無いこと**。仮説3へ

### 仮説3 — コア価値そのもの（最重要）

> Rotash の価値は「自分ひとりでは作れなかった1週間」が見えることにある。
> しかし7分割の縦長スロットは 16:9 写真の**横幅を82%捨てる**ため、
> 風景・食事・街が構図として成立せず、7枚が顔ばかりになる。
> 結果、完成作品に「1週間」が写らない。

- **正しければ** 撮影画角と表示を分離すると写真が多様になる
- **検証** 20グループの完成作品を目視分類（自撮り / 人物 / 風景 / 物 / その他）
- **成功** 自撮り比率 **40%以下**、1作品に3カテゴリ以上が混在
- **失敗** 自撮り70%超が続く → **撮影画角の分離を LATER から MUST に繰り上げる**

> **この仮説が最優先である。** ここが崩れると、招待も共有も継続も意味を失う。
> 見栄えのしない7枚は、誰も共有せず、来週もやりたいと思わせない。

### 仮説4 — 出来事依存（R）

> 出来事（ライブ・合宿等）は S と K を上げるが、
> **7日目に理由そのものが消滅するため R を下げる。**
> Rotash が週次習慣なら、出来事のない週でも完成するはずである。

- **検証** 20グループのうち **2グループを「出来事なし」の対照群**にする。全グループの2週目完成率を1週目と比較
- **成功** 2週目完成率が1週目の **70%以上** / 対照群が出来事あり群と同水準
- **失敗** 対照群がほぼ完成しない → **Rotash はイベント用ツールであって週次習慣ではない**

**失敗＝終わりではない。** その場合は「毎週の習慣」から
「予定のたびに立てる7日間のツール」へ**ポジショニングを変更する**。
`GROWTH_STRATEGY.md` が前提とする R の意味が変わるので、戦略の作り直しが要る。

### 仮説5 — 出口（K）

> 完成作品は7人の名前と7日間の物語を持つため「これ何？」を生む。
> しかし現在の共有は 16:9 でブランド要素が無く、フィードで細い帯として消える。

- **正しければ** 9:16 のブランド化された画像にすると K が上がる
- **検証** 招待リンクの `?from={グループID}` で、**出来事の種類別**に K を出す
- **成功** **1種類でも K ≥ 0.5**（この1種類に絞れば成長が始まる）
- **失敗** どの種類も K < 0.1 → 共有物ではなく**作品の中身が弱い**（仮説3に戻る）

## 8. 施策の連鎖

単発ではなく、互いを強化する順序で並べる。

```
  M5 人数を cap 3〜7 に
      │  1人グループが「今日も自分」で死ぬのを止める
      ▼
  M1 招待リンク + 未完成作品画像
      │  3人に到達する。同時に ?from が付き、K が測れるようになる
      ▼
  M4 朝8時の通知
      │  毎日開く理由ができる → 完成率が上がる
      ▼
  M3 完成の瞬間 + タイトル
      │  「終わった」ではなく「1本増えた」。共有の起点ができる
      ▼
  M2 共有画像 9:16
      │  作品が外に出る → 「これ何？」が発生
      ▼
  ⑦ 途中経過（3/7）の共有
      │  シェア機会が週1回から最大6回に
      ▼
  ⑥ Firestore 集計
      │  出来事別に K が出る → 当たりの種類が分かる
      ▼
  ⑧ 当たった種類に絞って S を再開
      │
      └──→ M1 へ戻る（今度は手ではなくループが回す）
```

**M5 → M1 の順序が重要である。** cap を入れる前にリンクを配ると、
3人未満のグループが大量にでき、`GROWTH_STRATEGY.md` 0-1 の最悪シナリオを
広い範囲で再現してしまう。**先に体験が成立する下限を保証してから、人を入れる。**

## 9. 90日計画

前提：開発者1名。M1〜M5 の実装が主。マーケティング予算ゼロ。

### Week 1–2 — 測れるようにする / 名簿を作る

| | 内容 |
|---|---|
| **目的** | 施策の前に、誤診を防ぐ土台を作る |

| **失敗時の次アクション** | 実装を止めて、先にビーチヘッド（誰の周辺で戦うか）を再選定する。**20人挙げられない状態で公開しても S は積み上がらない** |

### Week 3–4 — ループの部品を作り切る

| | 内容 |
|---|---|
| **目的** | ループを物理的に1周できる状態にする |

| **リソース** | 実装 10〜12日 |
| **KPI** | 5部品すべてが実機で動く |

| **失敗時** | 仮説1が誤り。招待の実装ではなく**誘う動機が無い**。Week 1–2 の名簿選定に戻る |

### Month 2 — 20グループを、出来事別に走らせる

| | 内容 |
|---|---|
| **目的** | 検証とコンテンツ生産を同時に走らせる |
| **実行** | ① 残り15グループを起動。**出来事の種類をわざとバラし、「出来事なし」を2つ必ず入れる** ② 各グループに種類ラベルを付ける ③ 週次で Firestore を集計 ④ 完成作品を目視分類（仮説3） ⑤ 20人にインタビュー（`PRODUCT_PHILOSOPHY` 30 の質問） |

| **失敗基準** | **2週目完成率が1週目の半分以下** → 仮説4が真。イベントツールへの再ポジショニングを検討 |
| | **自撮り70%超** → 仮説3が真。撮影画角の分離を MUST に繰り上げ、Month 3 を実装に充てる |

### Month 3 — S を止めて、正直に測る

| | 内容 |
|---|---|
| **目的** | 自分の労力とループの成果を分離する |
| **実行** | ① **新規グループの手動立ち上げを完全に停止** ② 4週間、WCG の推移だけを見る ③ 出来事別 K の表を完成させる |
| **KPI** | `R + K`（S を混ぜない実測値） |
| **成功基準** | **`R + K > 1`**、または **K ≥ 0.5 の出来事種類が1つ以上** |
| **失敗基準** | 全種類で K < 0.1 かつ R < 0.4 |
| **成功時の次アクション** | 当たった種類に絞って S を再開。Phase 2（発信者・コラボ）へ |
| **失敗時の次アクション** | **広告に逃げない。** 仮説3（写真の中身）に戻る。90日を追加してコアを作り直す |

## 10. Executive Summary

### 現在の最大の問題

**これは成長の問題ではなく、Pre-PMF の問題である。**
プロダクトは生後7日、未公開、ユーザーほぼゼロ、定量指標12項目すべて未取得。
そしてループを構成する部品 —— 招待リンク・通知・ブランド化された共有画像・計測 ——
が**1つも実装されていない**。いま獲得施策を打つと、費用を失うだけでなく
**「つまらない」という誤ったデータを得る**。

### 最大の成長機会

**「1人では作品が完成しない」という構造。**
Instagram・Locket・BeReal は1人で完結することが価値なので、
**追随した瞬間に自分のコアを壊す。大手が構造的に真似できない領域**に立っている。
問題はこの優位が**まだコードに存在しない**こと（1人でも7枚完成できてしまう）。

### 最重要 Growth Loop

```
予定を控えた言い出しっぺ
  → 3〜7人で起動（定員7の1枠として誘う）
  → 朝8時「今日は◯◯」で毎日開く
  → 7枚完成、最後の1人がタイトルを付ける
  → 9:16 の作品として外に出る
  → 「この7人、何してるんだ？」
  → 別の言い出しっぺが自分の予定で起動
```

### 最重要施策 TOP5

**M5 人数 cap → M1 招待リンク → M4 朝の通知 → M3 完成とタイトル → M2 9:16 共有画像。**
この順序に意味がある（cap を入れる前に人を入れると1人グループを量産する）。

### 最初の30日でやること

**マーケティングを1つもやらない。**
M1〜M5 を実装し、Firestore 集計スクリプトを書き、
**「来週予定があって、それを一緒に過ごす6人がいる人」を実名で20人書き出す。**

### 90日後に目指す状態

20グループが実際に7日間を完走し、出来事の種類別に K が出ていて、
**S を止めても WCG が横ばい以上**であること。ユーザー数ではなく、
**「作品を完成させたグループ数」で語れる状態**になっていること。

### 最大のリスク

**7分割の縦長スロットが 16:9 写真の横幅を 82% 捨てるため、7枚が顔ばかりになること。**
見栄えのしない7枚は共有されず、来週もやりたいと思わせない。
**この1点が崩れると、招待も通知も共有も継続も、すべて意味を失う。**
Month 2 の目視分類で自撮り70%超なら、撮影画角の分離を最優先に繰り上げる。

### 経営判断として「やらないこと」

| やらない | 理由 |
|---|---|
| **広告（Web / App Store）** | 個人を連れてくる。3人に届かず死に、誤ったデータを残す |
| **タイムライン / いいね / フォロワー** | 作品が外部評価の対象になった瞬間、日常が撮れなくなる（BeReal が壊れた道筋） |
| **連続週数（streak）** | 7人依存で毎週約30%壊れ、壊れたとき相互非難が起きる |
| **グループ横断のネットワーク効果** | Rotash は Network Effect を意図的に7人で打ち止めにする。超えた分はノイズ |
| **Android・マネタイズ・複数グループ** | PMF 前の分散。90日では触らない |

## 11. 最後に — 都合の良い結論を出さないために

依頼の指示に従い、成長可能性が低い箇所は明示する。

**厳しい事実：**

1. **コアがまだ1度も外部検証されていない。** 開発者本人が「本当に面白くない」と
   自分の写真について書いている（`PRODUCT_PHILOSOPHY` 5）。これは軽い所見ではない
2. **「出来事のない普通の1週間」で成立するかは、五分五分だと見ている。**
   成立しなければ週次習慣ではなくイベントツールであり、事業の形が変わる
3. **開発者1名・iOS のみ・生後7日**。90日でできるのは MUST を作り切って
   20グループを走らせるところまでで、それ以上を計画に入れるのは非現実的である

**それでも取り組む価値があると判断する理由：**

構造的優位（1人では完成しない）は本物で、大手が追随できない。
そして検証コストが低い —— **20グループ = 60〜140人**で答えが出る。
広告費ゼロ、90日、実装 MUST 5項目。**賭け金が小さく、当たったときの防御力が高い。**

**ただし、その判断が正しいかどうかは、Month 2 の「2週目の完成率」で決まる。**
そこが半分以下に落ちたら、戦略ではなくプロダクトの前提を作り直すこと。
