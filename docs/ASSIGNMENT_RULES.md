# 担当の決め方（2026-10-19 に作り変えた）

コードは `Rotash/Services/AssignmentPlanner.swift`（1日ずつ選ぶ）、`AssignmentHistory.swift`（これまでの記録）、
`AssignmentAudit.swift`（アプリを開くたびに今日より先を組み直す）、`AppViewModel.rolledWeek`（月曜に1週間を組む）。
同じ手順を Python に写したシミュレーションが `tools/assignment-sim.py`（Swift を変えたら、こちらも同じように変える）。

## 1. 何が起きたか

2026-10 の最初の週、3人のグループで、オーナーの番が火曜にあったあと、**水・木・金・土と番が来なかった**
（オーナー自身のアンケート。日曜も来なかったと本人は話している）。
火曜にオーナーが撮ったあと、同じ火曜に友達を1人追加し、その友達は翌日（水曜）に番が来ていた。

## 2. 原因（以前の決め方）

3つが重なっていた。

1. **累計の担当回数が少ない人を先にする。** 新しく入った人は 0 回なので、列の先頭に割り込む
2. **アプリを開くたびに、今日より先の日を組み直す**（`AssignmentAudit.repaired`。起動時と同期のたび）
3. **組み直すのは今週の残りの日だけ**で、待っている日数は見ていなかった

累計が多い人は、毎日の組み直しのたびに後ろへ押され、週の終わりを越えてしまう。
以前の決め方を写したシミュレーションでは、オーナーと同じ週で:

| 条件 | オーナーに日曜まで番が来なかった割合 |
|---|---|
| 3人の累計が同じ | 約 25% |
| オーナーが1回多く番を持っていた | 約 75% |

ほかにも見つかったこと:

- 週の途中で組み直すとき、残りの日だけで回数を揃えていたので、3/2/2 のはずが 3/3/1 などになる週が 9〜25% あった
- 長く続いたグループに新しい人が入ると、その人に番が集中した（3人で10週続けたところに4人目が入ると、4人目が4週間の46%の日を担当し、前からいる人は最大10日待った）

## 3. いまの決め方

1日ずつ、次の順に候補を絞り、最後に残った人からランダムに選ぶ（種つきなので、どの端末でも同じ表になる）。

1. **その週の担当回数をできるだけ均等に**（2人=4/3、3人=3/2/2 …）。週の途中で組み直すときも、過ぎた日の担当を数に入れる
2. **誰も「人数+1日」を超えて待たせない。** 番から次の番まで、3人なら最大4日、7人なら最大8日。
   まだ番が無い人は「入った日」を最後の番とみなす（入ってから人数+1日以内に最初の番が来る）。
   1 の回数の上限の中で守れなければ回数の上限を緩め、それでも守れなければ（人が抜けた直後など）いちばん長く待っている人
3. 同じ人の2日連続を避ける
4. **累計の担当回数が少ない人を先に。** 新しく入った人は、入った時点で前からいた人のうち最も少ない回数から数える。
   抜けて入り直した人は、前の自分の回数とその値の多い方から
5. 前の週の同じ曜日と同じ人を避ける
6. 残った人からランダム

「待てる日数」が守れるかどうかは、「これから k 日のうちに期限が来る人が k 人以下か」で確かめている
（期限の早い人から1日1人ずつ割り当てられるか、と同じ）。

設定は `RotashFeatureFlags.turnGapAllowance`（人数に足す日数。いまは 1。nil で上限なし）。
0 にすると毎日1人に決まる完全な順番回しになり、次が誰か当てられてしまうので使わない。

## 4. 確かめた結果（`tools/assignment-sim.py`、2026-10-19）

### 人数が変わらない運用（1500週）

| 人数 | 最大の間隔 | 人数+1を超えた間隔 | 週の回数差の最大 | 次の担当を1人に絞れる日（前→今） | ルールを知っている人が当てられる確率（前→今） |
|---|---|---|---|---|---|
| 2 | 2日 | 0% | 1 | 100% → 100% | 100% → 100% |
| 3 | 4日（前は5日） | 0%（前は4.7%） | 1 | 63.5% → 61.4% | 81.7% → 80.7% |
| 4 | 5日（前は7日） | 0%（前は13.5%） | 1 | 38.8% → 71.5% | 67.7% → 85.4% |
| 5 | 6日（前は9日） | 0%（前は16.4%） | 1 | 25.0% → 55.3% | 53.5% → 71.4% |
| 6 | 7日（前は11日） | 0%（前は31.6%） | 1 | 20.6% → 60.4% | 46.4% → 71.8% |
| 7 | 8日（前は13日） | 0%（前は28.5%） | 0 | 18.3% → 76.4% | 42.2% → 82.7% |

- **3人まではランダムさがほとんど変わらない。** 2人はもともと交互（ABAB…）で、前から当て放題
- **4人以上ではランダムさが減る**（「次は誰か分からない」が弱くなる）。待つ日数の上限と引き換え。
  気になるなら `turnGapAllowance` を 2 にすると、待つ日数は「人数+2日」まで延びるかわりにランダムさが戻る

### オーナーと同じ週（火曜にオーナーが撮り、同じ火曜に友達が入った）

| 条件 | 木 | 金 | 土 | 日曜まで来ない |
|---|---|---|---|---|
| 3人の累計が同じ | 49.8% | 24.4% | 25.8% | **0%**（前は約25%） |
| オーナーが1回多い | 0% | 49.8% | 50.2% | **0%**（前は約75%） |

### 3人で10週続けたところへ、水曜に4人目が入る（そのあと4週間）

- 前からいる人の最大の待ち: 5日（前は最大10日）
- 新しい人の担当の割合: 24.7%（4人なら理想は25%。前は46%）

### 1人抜ける

人数が減ると上限も1日縮むので、抜けた直後に守れない日が出ることがある（その週に出た割合: 4→3人で約7%、7→6人で約18%）。
**超えても1日だけ**で、次の日からは上限の中に戻る。

## 5. テスト

`RotashTests/AssignmentTests.swift` に足した（Xcode の ⌘U で動かす）。

- `testNobodyWaitsLongerThanMembersPlusOneDays` … 300通りの種で、誰も4日を超えて待たない
- `testWeekCountsIncludeDaysAlreadyAssigned` … 週の途中で組み直しても 3/2/2
- `testOwnerGetsATurnWithinTheLimitAfterAFriendJoins` … オーナーと同じ週で、土曜までに必ずオーナーの番が来る
- `testNewcomerStartsFromTheLowestCountOfThoseAlreadyThere` … 新しい人は前からいた人の最小の回数から
- `testLastTurnOfSomeoneWithoutATurnIsTheDayTheyJoined` … 番の無い人は入った日を最後の番とみなす

同じ条件を Python に写して先に確かめてある（どれも違反0件）。
**この変更を書いた環境では Swift を動かせなかった**ので、Xcode でビルドとテストを通してから TestFlight に出すこと。
