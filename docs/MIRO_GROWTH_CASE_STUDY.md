# Miro — 成長事例からの構造抽出と Rotash への応用

[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md)・[`TIMETREE_GROWTH_CASE_STUDY.md`](TIMETREE_GROWTH_CASE_STUDY.md) の続き。
Miroはオンラインホワイトボードの**B2B SaaS**であり、今までの2つ（個人習慣アプリ／個人〜家族向け共有ツール）
とは異なり、**「プロダクト主導成長（PLG: Product-Led Growth）」の代表事例**として語られることが多い。
個人向けアプリのRotashにB2B SaaSをそのまま持ち込むことはできないが、
**「共有した瞬間に相手も価値を体験し、それが次の招待を生む」というバイラルの作り方**は、
業種を超えて参照できる部分が多い。

## 0. Miroの規模と概要（事実）

**Rotashとの位置づけの違い：** Miroは「B2Bで、機能的価値（Functional Value）が強く、
組織内に無制限に人を増やしたいプロダクト」である。`GROWTH_DIAGNOSIS.md` §5 の分類で言えば、
TimeTree同様Functional寄りであり、Network Valueで戦うRotashとは価値の源泉が異なる。
**この資料が扱うのは機能の話ではなく、「バイラルをどう作ったか」という成長の型の話である。**

## 1. フリーミアムの軸を「人数」ではなく「資源（ボード数）」に置く設計

Miroの無料プランは**チームメンバーを無制限に招待できる**一方、**編集・共有できるボードは3枚まで**
という制限がある。つまり「招待する人数」には一切課金しない。
[（出典）](https://app-tatsujin.com/miro-free-plan-features-limitations-2026/)

これは意図的な設計である。**招待に課金すると、招待そのものにブレーキがかかる。**
Miroは招待を無料にすることで、社内に人が増えれば増えるほどプロダクトの価値が上がる
（=バイラルが自然に起きる）状態を作り、**その後で「ボードが足りない」という
別の理由から課金に至らせている。**

### Rotashへの示唆：既に同じ設計思想を持っている

Rotashは現在マネタイズを設計していない（`GROWTH_DIAGNOSIS.md` §1「やらないこと」）。
将来課金を検討する時期が来た際の**指針**として、この原則はそのまま使える：

> **人数（＝3〜7人という定員）には絶対に課金しない。**
> 課金するとしたら、[`TIMETREE_GROWTH_CASE_STUDY.md`](TIMETREE_GROWTH_CASE_STUDY.md) §4で
> 既に出した結論と同じく、複数グループ数（`GROWTH_STRATEGY.md` L2）やMemoriesの高度な表現など、
> **人数にも作品の完成にも関係ない拡張だけ**を課金対象にする。

**→ 判定：LATER（既存のマネタイズ方針を補強する原則として記録）。**
新しい実装課題は生まれない。「人数に課金しない」という一点だけを、
将来のための明文化された制約として追加する。

## 2. 外部共有が招待ではなく「体験」から始まる — Rotashの設計と本質的に同じ構造

Miroのバイラルループの核心は、**招待を頼む前に、相手が先に価値を体験すること**にある。
ブランドエージェンシーがクライアントとボードを共有すると、クライアントはそのボードを見て
（時に編集して）価値を実感し、その体験が新しいアカウント作成につながる。
これが「外部バイラルループ」と呼ばれる構造である。
[（出典）](https://medium.com/pm101/how-miro-grows-tactical-lessons-from-the-17-5b-whiteboard-f56ec812f500)

さらに特筆すべきは、Miroの成長チームが**「1人のユーザーが何人を新たに連れてくるか」を
最重要指標として執拗に追跡し、高い目標を掲げて改善し続けた**という運用の姿勢である。
[（出典）](https://blog.allstarsaas.com/posts/miro-plg)

### Rotashへの示唆：構造は正しい。欠けているのは「執拗な計測」である

**構造そのものは新しい発見ではない。** これは `GROWTH_STRATEGY.md` D-1〜D-2
（「招待して」ではなく「作品を完成させるために友達が必要」という状態を作る）と
まったく同じ原理であり、Miroの事例は**独立した業種からの強い裏付け**になる。

新しい示唆は、**運用の姿勢**の方にある。

> Miroは「1人が何人連れてくるか」を、単に測るだけでなく**執拗に（relentlessly）**
> 追い続けたと明言している。Rotashの `GROWTH_DIAGNOSIS.md` K-3 は既に同じ指標
> （K = 作品あたり新規グループ数）をNorth Star Metricの補助指標として定義しているが、
> **これを「一度作って終わり」にせず、Miroのように継続的に改善対象として追い続ける
> 運用文化が必要**だという点が、この事例が付け加える唯一の実務的な教訓である。

**→ 判定：確認 + 運用姿勢の強調。** `GROWTH_DIAGNOSIS.md` Month 3（「Sを止めて、正直に測る」）
の期間だけでなく、**K指標の計測と改善はその後も止めないこと**を明記する。

## 3. テンプレートギャラリー — 「空白のキャンバスを見せない」ことの大規模な実証

Miroは300種類以上のテンプレートを用意し、ユーザーは空白のホワイトボードではなく
**テンプレートを選ぶだけ**で使い始められる。テンプレートはSEO流入の入口にもなっている。
[（出典）](https://aslead.nri.co.jp/products/miro/column/miro-function-plan-explanation.html)

### Rotashへの示唆：既存方針（D-4・S6）の裏付け

これは新しい示唆ではなく、`GROWTH_STRATEGY.md` D-4（1〜2人のときも撮影は禁止しない）・
L-2 S6（参加直後に既存の枠を見せる。空のキャンバスを見せない）という
**既存の原則がMiroの規模でも通用する一般原則であること**の確認である。

**→ 判定：確認のみ。** 新しい施策は生まれない。

## 4. Land and Expand — Rotashにとって唯一の新しい示唆

Miro最大の特徴は、**契約してから配る（あすけんのB2B2C型）のではなく、
1人・1チームが自発的に使い始め、その価値が社内で自然に伝播し、
後から会社が正式に契約する**という順序である。「個人の無料利用」が
「チームでの利用」を経て「法人契約」に至る、**ボトムアップ型の拡大**である。

### Rotashへの示唆：Phase 2の「団体展開」に、もう1つの入り口を加える

[`ASKEN_GROWTH_CASE_STUDY.md`](ASKEN_GROWTH_CASE_STUDY.md) §5 で検討した法人・団体配布チャネルは、
**トップダウン型**（代表者と先に交渉し、そこから7人単位に分割する）だった。
Miroの事例は、これとは逆向きの、もう1つの経路を示す：

```
トップダウン型（あすけん型、既存§5の提案）：
  代表者を口説く → 承諾を得る → 7人単位に分割して配る

ボトムアップ型（Miro型、この節の新しい示唆）：
  言い出しっぺが自分の7人組で普通に使う
    → その週の完成作品が良かった
    → 「サークルの他の代でもやろう」と自然に伝播する
    → 複数の7人組が同じサークル内で並行して生まれる
    → その時点で初めて、サークル代表に「まとめて案内しようか」と持ちかける
```

**この順序の方が、Rotashの現在の設計思想に忠実である。** `GROWTH_STRATEGY.md` 全体が
「決断を迫らない」「誘われた側に説明を要求しない」ことを一貫した原則としている
（B-3, D-1）。トップダウンでの団体導入は、その団体に所属する全員に対して
**外側から一斉に「使ってください」と決断を迫る**ことになりやすく、Rotashが避けてきた
構造と衝突するリスクがある。**Miro型のボトムアップ拡大は、この衝突を避けられる。**

**→ 判定：`ASKEN_GROWTH_CASE_STUDY.md` §5 の実行順序に対する補足を追加する。**
団体への持ち込みは、**まず個人の言い出しっぺ経由で自然発生させ、実際に良い結果が出た
グループが複数生まれてから、初めて代表者へ「まとめませんか」と持ちかける**のが正しい順序である。
最初から代表者を起点にトップダウンで持ち込むのは、`GROWTH_DIAGNOSIS.md` の
Pre-PMF診断（コアがまだ検証されていない）と合わせて、**さらにリスクが高い**ことが確認できた。

## 5. まとめ

| 節 | 判定 | 既存資料との関係 |
|---|---|---|
| §1 人数ではなく資源に課金 | **LATER**（原則を記録） | マネタイズ方針が未設計の間の指針として追加 |
| §2 外部共有からの流入＋執拗な計測文化 | **確認＋運用姿勢の強調** | D-1〜D-2、K-3を裏付け。**計測を止めない**ことを明記 |
| §3 テンプレートギャラリー | **確認のみ** | D-4・S6の裏付け |
| §4 Land and Expand（ボトムアップ拡大） | **`ASKEN_GROWTH_CASE_STUDY.md` §5への補足** | 唯一の新しい示唆。団体展開はトップダウンでなくボトムアップを先に試す |

**この資料の結論：**
MiroはB2B SaaSであり、Rotashに直接移植できる機能的な示唆はほとんど無い。
**唯一かつ最も重要な発見は§4——法人・団体への展開順序**である。
`ASKEN_GROWTH_CASE_STUDY.md` が示したトップダウン型（あすけんの健保組合モデル）だけでなく、
**Rotash自身の「決断を迫らない」という設計思想に沿うのは、Miro型のボトムアップ拡大の方である**
という、既存の法人展開案に対する重要な修正を加えることができた。
