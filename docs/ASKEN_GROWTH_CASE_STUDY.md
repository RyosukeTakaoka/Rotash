# あすけん — 成長事例からの構造抽出と Rotash への応用

この資料は [`GROWTH_STRATEGY.md`](GROWTH_STRATEGY.md) セクション H（競合・成功事例からの構造抽出）に対する追補である。
H では BeReal / Locket / Wordle / Duolingo / Snapchat / Pokémon GO という**海外のソーシャル/ゲーム系アプリ**を扱った。

この資料が扱う「あすけん」は、それらと根本的に性質が違う。

> あすけんは **1人で完結する日々の習慣アプリ**（食事管理）であり、
> Rotash が置いている **「7人でなければ成立しない」という制約を持たない。**

だからこそ、H の6事例が示さなかった2つの視点——
**「個人の習慣をどう長期化させるか」**と**「広告費ゼロでどう配布網を作るか」**——
を補うケースとして意味がある。GROWTH_STRATEGY.md の語彙（MUST/SHOULD/LATER/DON'T、M1〜M5、J章）と
North Star Metric（WCG、K-3 の指標）にそのまま接続する形で書く。

**この資料の結論を先に言うと：**
あすけんの施策のほとんどは、**Rotashが既に別の理由で辿り着いた結論と同じ方向を指している**
（通知の作法、streakを避けたこと等）。**ただし1つだけ、Rotashにまだ無い強力なレバーがある。
それが末尾の「機会 α：法人・団体配布チャネル」である。**

**「なぜ1,400万人が離脱しなかったか」の構造**だけである。

## 1. AI栄養士キャラクター「みきちゃん」— 情緒的フィードバックがリテンションを作る

あすけんの中核体験は、食事を記録すると**AI栄養士キャラクター「みきちゃん」**が
「糖質が多いですね」「タンパク質が足りていません」のように**人格を持った声で**フィードバックを返すことである。
[（出典）](https://news.mynavi.jp/article/20210914-1971945/)

これは単なるデータ表示ではない。**「今日は何て言われるかな」という、Rotashの「今日は誰？」と同じ構造の期待**を、
1日1回・個人単位で作っている。

### Rotashへの示唆：適用できない理由がRotashには既にある

一見、「今日は誰？」の通知に人格や台詞を足したくなるが、**やらない方がよい。**

`GROWTH_STRATEGY.md` J-1 と F-3 で既に、Rotashの通知は
「友達についての通知か、アプリについての通知か」だけを基準にすると決めている。
あすけんの「みきちゃん」はアプリ（＝AI）が主語の声であり、Rotashに人格キャラクターを足すと、
**「今日はMINA」という友達本人の名前の力を、キャラクターの声が薄める。**

**→ 判定：DON'T（追加しない）。** ただし下の§3で触れる通り、**文面の作法**だけは学ぶ価値がある。

## 2. 点数化・ゲーミフィケーション — Rotashで最も危険な誘惑

あすけんは食事内容を**点数（スコア）**として可視化し、栄養バランスの改善を促す。
この設計は Japan Gamification Association が事例分析するほど作り込まれている。
[（出典）](https://note.com/jgamifa/n/n61c0d8b48ef5)

これは強力な機構である。**しかしRotashで最も注意すべき事例でもある。**

### なぜあすけんでは機能し、Rotashでは機能しないか

| | あすけんの点数 | Rotashで同じことをした場合 |
|---|---|---|
| 評価の対象 | **自分の食事だけ**（個人単位） | 7人の共同作業（グループ単位） |
| 低い点数が出たとき | 自分だけが見る。恥をかく相手がいない | 7人全員が見る。**誰が足を引っ張ったか分かる** |
| 心理的効果 | 自己改善の動機 | **相互監視・相互非難** |

これは `GROWTH_STRATEGY.md` C-1（連続週数を実装しない理由）・
J-1 #2（個人の撮影率・貢献度・サボり検知は禁止）と**まったく同じ理由**で失敗する。
あすけんの点数化が個人向けだから安全に機能しているのであって、
**「点数化」という手法自体がRotashに安全に移植できるわけではない。**

**→ 判定：DON'T（J-1 #2 に該当。理由を1件補強）。**
「あすけんも点数化していないか？」という問いが将来出た場合、この節を参照すること。

## 3. プッシュ通知の作法 — Rotashの現在の設計が正しかったことの裏付け

あすけんはプッシュ通知の効果を検証しており、公開されている知見がそのまま使える。
[（出典1：Repro導入事例）](https://repro.io/casestudy/interview_asuken/)
[（出典2：アプリマ）](https://marketing.sendai.garden/%E3%83%AA%E3%83%86%E3%83%B3%E3%82%B7%E3%83%A7%E3%83%B3%E7%8E%877%E3%83%9D%E3%82%A4%E3%83%B3%E3%83%88%E6%94%B9%E5%96%84%EF%BC%81%E3%80%8E%E3%81%82%E3%81%99%E3%81%91%E3%82%93%E3%80%8F%E3%81%AE%E3%82%A2/)

事実：

- 通知対象を**3セグメント**に分けている（①会員登録未完了、②1回も記録なし、③定期記録者）
- 施策後、**初回記録率 +8pt**、**新規ユーザーの7日後リテンション +4pt**、**記録ユーザーの7日後リテンション +1pt**
- 効いた工夫：**キャラクターの名前を文面に入れる**・**悲しい表情の絵文字を使う**
- **煽り気味の文言は失敗した**

### Rotashへの示唆：新しい示唆ではなく、既存設計の裏付け

これは新しい発見ではない。`GROWTH_STRATEGY.md` F-3 / J-1 #8 は既に
**「催促通知の複数回送信は義務化の入口」**として禁止しており、
1日最大2通・「友達についての通知」のみという原則を立てている。

あすけんの実データは、**この原則が正しい方向であることの独立した裏付けになる。**
特に「煽り気味の文言が失敗する」という結果は、
Rotashが `L-4` で禁じた「あと2枚で完成！」的な進捗の煽りと同じ失敗パターンである。

一方で**1点だけ、Rotashにまだ反映されていない実務上のヒント**がある：

> **セグメント別に通知の中身を変える発想。**
> あすけんは「登録すらしていない人」「記録ゼロの人」「継続している人」に別の通知を送っている。
> Rotashにも構造的に同じ3段階が存在する：
> **①招待を受け取ったが未参加**／**②参加したがまだ3人未満（0-4の"開始前"状態）**／**③3人以上で日次ループが回っている**。
> 現在 F-3 の通知設計は③だけを対象にしている。①②向けの通知（例：招待コードが開封されてから24時間、
> まだ参加していない人へ1回だけ）は、`GROWTH_DIAGNOSIS.md` 仮説1（3人到達率）を直接押し上げる余地がある。

**→ 判定：SHOULD（新規番号 S9 として追加を提案）。**
ただし「未参加者へのリマインド」は**招待した本人ではなく招待された側に届く通知**であり、
J-1 #8 の「催促」に該当しないよう、**1回だけ・「◯◯があなたを待っています」ではなく
「◯◯の1週間、まだ空きがあります」というRotashの作品ベースの文体を守ること**（D-3 の原則をそのまま適用）。

## 4. お友達紹介機能 — あすけんにもK施策はある

あすけんは2020年12月に**お友達紹介機能**を追加し、期間限定キャンペーンを実施している。
[（出典）](https://www.asken.inc/news/2020/12/28)

あすけんは個人の習慣アプリでバイラル係数が本質的に低いはずだが、
**それでも紹介施策を後付けで実装している**という事実は示唆的である。
個人利用が前提のアプリですら、**紹介の起点を明示的に作らないとKはゼロに近いまま**だということである。

### Rotashへの示唆

Rotashは `GROWTH_STRATEGY.md` D 章の通り、**「招待して」と頼まずに招待が起きる構造**
（7枠のうち空きがある、という事実だけで誘発する）を目指しており、これはあすけんの
「紹介キャンペーン」（インセンティブ付きの明示的な依頼）とは**設計思想が逆**である。

**Rotashの設計の方が筋が良い。** あすけんが紹介機能を「後から追加」せざるを得なかったのは、
個人利用アプリには構造的に招待の理由がないからであり、Rotashは招待理由を製品の中心に持っている
（M1・D-1〜D-3）。**→ この節から得る結論は「あすけんを真似て紹介キャンペーンを足す」ではなく
「M1（招待リンク+未完成作品画像）を軽視してはいけない」という既存MUSTの優先度の再確認である。**
あすけんほど強い構造的優位を持たないアプリでさえ、招待導線に投資してKを作った。

## 5. 機会 α：法人・団体配布チャネル（Rotashにまだ無い最大のレバー）

ここが、この資料で**唯一、既存の GROWTH_STRATEGY.md に無い新しい示唆**である。

### 事実

あすけんは個人課金だけでなく、**法人・健康保険組合・自治体向けの「あすけんプラス」**という
B2B2C チャネルを持つ。企業の人事・総務や健保組合が契約し、**そこに所属する従業員・被保険者へ
一括で配布される。**
[（出典1）](https://www.asken.jp/lp/corporation/)
[（出典2：学研健康保険組合の導入事例）](https://g-kenpo.or.jp/service/page-13428/asken/)

さらに「あすけん式健康づくりプログラム」という特定保健指導サービスも同じ経路で展開している。
[（出典）](https://prtimes.jp/main/html/rd/p/000000193.000058653.000058653)

**この経路の強さは、単価の低い一人ずつの獲得と根本的に違う。**
1つの健保組合との契約が、数千〜数万人への配布に一度で変わる。
広告費をかけて1人ずつ獲得するB2Cの経済とは、獲得コストの桁が違う。

### Rotashへの示唆：既存のPhase 2施策の優先度を上げる根拠になる

`GROWTH_DIAGNOSIS.md` §7 の施策リストに、既に近い発想が入っている：

- 施策17「既に7人で動いている発信者に渡す」
- 施策18「学園祭実行委員・ライブ主催とのコラボ」（Phase 2 / 優先度「低」）

あすけんの事例は、**この2つが単発の思いつきではなく、実際に機能する配布モデルの類型である**
ことを示す。ただし違いも明確にしておく必要がある：

| | あすけん（B2B2C） | Rotashで想定される類型 |
|---|---|---|
| 契約主体 | 健保組合・企業人事（組織） | サークル代表・実行委員長・幹事（個人〜非公式団体） |
| 配布単位 | 従業員全員に一括配布 | **7人という定員があるため、一括配布ができない** |
| Rotashの制約 | — | 100人のサークルに配っても、7人ずつのグループに**手動で分割**しないと機能しない（`GROWTH_DIAGNOSIS.md` L2「複数グループ」が前提） |

**つまりRotashは、あすけんと同じ配布力学をそのまま使えない。**
7人という上限（0-2 の設計判断）が、B2B2C的な「一括配布」と構造的に相性が悪いためである。

**それでも学べる点は1つに絞れる：**

> **「代表者1人と契約すれば、その先の人数分が自動的に付いてくる」経路を探す。**
> あすけんは組織（健保組合）がそれだが、Rotashにとっての等価物は
> **「既に7〜21人程度の固定メンバーで定期的に集まっている場」**
> （サークルの代の集まり、部活の学年、卒業旅行の幹事団）である。
> 1人の幹事を口説けば、7人×1〜3グループが一度に立つ。
> これは `GROWTH_DIAGNOSIS.md` の「言い出しっぺ20人」探しを、
> **「1人ずつ20人」ではなく「代表者を通じて7人単位」で探す**という探索方法の変更を意味する。

**→ 判定：`GROWTH_DIAGNOSIS.md` 施策17・18 は「低」ではなく Month 2 以降の
S（人力で立てたグループ数）獲得の主経路として明示的に位置づけ直すことを提案する。**
ただし Pre-PMF 診断（`GROWTH_DIAGNOSIS.md` §2）の結論は変わらない。
**コアが検証される前に団体へ持ち込むと、あすけんと違って「つまらない」という
誤ったデータを組織単位で量産するリスクがある。** 90日計画の Month 1–2（個人ベースの20グループ）
が先であることに変更はない。

## 6. 集計データを使ったPR — Rotashが手の届く範囲でできること

あすけんは「痩せた人の総減量数は8,440トン」のような、**自社の利用データを集計した数字**を
プレスリリース化し、メディアに取り上げられている。
[（出典）](https://dengekionline.com/article/202406/8271)

広告費をかけずに、**自分たちが持っているデータそのものをコンテンツにする**手法である。

### Rotashへの示唆

`GROWTH_DIAGNOSIS.md` 施策6「Firestore集計スクリプト」・L-2 の S8 は、
現状「診断のための計測」として位置づけられている。
あすけんの事例は、**同じ集計が診断だけでなくPR素材にもなる**ことを示す。

例：「完成した作品の何%が3人以上で作られたか」「1グループが平均何週続いたか」——
これらは `tools/rotash-stats.py` が既に持っている生データの延長で作れる。

**→ 判定：LATER。** `GROWTH_DIAGNOSIS.md` Month 3 で「S を止めて正直に測る」段階に到達し、
かつ胸を張れる数字（例：R+K > 1、または2週目完成率70%超）が出てから使う。
**数字が悪いうちにPR化すると逆効果になる**のは、あすけんに限らず一般原則である。

## 7. まとめ — この資料が GROWTH_STRATEGY.md に追加する差分

| 節 | 判定 | 既存資料との関係 |
|---|---|---|
| §1 AI栄養士キャラクター | **DON'T** | J-1 を補強（アプリ主語の声は友達主語の通知を弱める） |
| §2 点数化・ゲーミフィケーション | **DON'T** | C-1・J-1 #2 を補強（個人向けの手法はグループ向けに転用できない） |
| §3 プッシュ通知の作法 | 既存設計の**裏付け** + **新規 SHOULD 案（S9）** | F-3 の原則が正しいことの外部エビデンス。未参加者向け通知は新規提案 |
| §4 お友達紹介機能 | **既存MUSTの優先度確認** | M1 を弱めない理由の補強。新規施策は提案しない |
| §5 法人・団体配布チャネル | **既存Phase2施策(17・18)の位置づけ強化** | 唯一の新しい構造的示唆。ただしRotashの7人上限により**そのままは使えない**ことも明記 |
| §6 集計データPR | **LATER** | S8 の使い道を拡張する提案 |

**この資料の最も重要な発見は、否定的な結果である：**
あすけんの主要な成長装置（キャラクター・点数化）の**大半はRotashに移植すべきではない**。
理由は目新しいものではなく、Rotashが `GROWTH_STRATEGY.md` で既に独自に辿り着いていた
「個人向け施策をグループに持ち込むと相互監視になる」という結論と、毎回一致する。

**移植できるのは1つだけ：法人・団体という配布チャネルの発想（§5）。**
ただしそれも「上限7人」という Rotash の根幹設計とぶつかるため、**そのままではなく
「代表者経由で7人単位に分割する」という形に組み替えて初めて使える。**
