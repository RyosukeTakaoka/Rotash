# Rotash — ゼロ週目の戦略（Go To Market）

[`docs/GROWTH_STRATEGY.md`](GROWTH_STRATEGY.md) は、**ループが回り始めた後**をどう強くするかの資料である。

この資料は、その手前 —— **ループにまだ何も乗っていない状態から、最初の1周をどう作るか** を扱う。

---

## 0. 前の資料の欠陥を先に認める

`GROWTH_STRATEGY.md` はこう書いた。

```
WCG(来週) = WCG(今週) × ( R + K )

  成長条件：R + K > 1
```

**この式には決定的な欠陥がある。WCG(今週) が 0 なら、R と K がいくら大きくても、来週も 0 である。**

```
0 × 1.5 = 0
0 × 3.0 = 0
0 × 100 = 0
```

ループの回し方だけを書いて、**最初の1周に何を乗せるか**を書いていなかった。

正しい式はこうなる。

```
WCG(t+1) = WCG(t) × ( R + K )  +  S(t)
                    ─────────      ────
                    ループが回す    手で作る

  S(t) = その週に、人力で立ち上げたグループ数
```

**リリース直後は、右辺の第1項がゼロである。S だけが全てだ。**

そしてこの構造は、「1.3万RT」の事例が言っていることと完全に一致する。

> バズは 0 → 10,000 ではなく、**誰かが 0 → 100 を作り、その 100 が 10,000 になる**。

あの著者は2年かけてライブ会場で100人の顔見知りを作っていた。だから投稿直後に自力で100RTを作れた。**バズは彼が作ったのではなく、彼が作った100が作った。**

## 1. 最も重要な転換：獲得の単位は「ユーザー」ではなく「言い出しっぺ」

ここが、Rotash と普通のアプリの決定的な違いである。

普通のアプリの獲得：

```
広告に1000円 → 1インストール → 1ユーザー
```

Rotash の獲得：

```
広告に1000円 → 1インストール → 1人ぼっちのグループ → 死亡
```

**Rotash では、1人のユーザーには何の価値もない。** 3人集まって初めて体験が成立する（`GROWTH_STRATEGY.md` 0-2）。つまり、

> **獲得すべきなのはユーザーではなく、「6人を呼べる1人」＝言い出しっぺである。**

さらに一段だけ精度を上げられる。言い出しっぺ1人では、まだ「誰を呼ぶか」と
「なぜ今週なのか」が決まっていない。**呼ぶ理由が要る。**

```
        獲得の単位 =  言い出しっぺ  ×  7日間の理由がある出来事
                     （6人を呼べる1人）   （ライブ / 合宿 / 文化祭 …）
```

- **言い出しっぺだけ**（出来事なし）→ 「今週やろう」と言えるが、撮る理由がない
- **出来事だけ**（言い出しっぺなし）→ 予定はあるが、誰も言い出さない
- **両方そろって初めて 1 グループが立つ**

だから Phase 0 で探すのは「Rotash を使いそうな人」ではない。
**「来週なにか予定があって、それを一緒に過ごす6人がいる1人」**である。

この違いは、あらゆる集客手法の評価をひっくり返す。

| | 個人を連れてくる手法 | 言い出しっぺを連れてくる手法 |
|---|---|---|
| 例 | Web広告 / App Store広告 / ASO / アプリ紹介メディア | 知人への直接依頼 / 既存グループごとの勧誘 / 実際に使ってもらう |
| 単価 | 安い | 高い（手間がかかる） |
| **成果** | **ほぼゼロ**（3人に届かず死ぬ） | **1人 = 1グループ = 3〜7人** |
| 初期の価値 | ほぼない | **これが全て** |

**15の集客手法の優先順位は、ROI では決まらない。「グループを連れてくるか、個人を連れてくるか」で決まる。** これが唯一の判定軸である。

### 15手法を、この1軸で並べ直す

| 手法 | 連れてくる単位 | ゼロ週目の価値 | 判定 |
|---|---|---|---|
| **知人への直接依頼** | **グループ** | **最大** | **これだけやる** |
| **既存コミュニティへの持ち込み**（部活・ゼミ・ライブ仲間） | **グループ** | **最大** | **これだけやる** |
| 口コミ・紹介 | グループ | 大（ただしユーザーが居ないと発生しない） | Phase 1 |
| インフルエンサー | 条件付き（後述） | 中 | Phase 2 |
| SNS発信 | 個人 → だが言い出しっぺを釣れる | 中 | Phase 1（発信内容が重要） |
| コラボ | グループ | 中 | Phase 2 |
| オフライン（学校・イベント） | グループ | 中 | Phase 2 |
| YouTuber / ブロガー | 個人 | 小 | Phase 2 |
| プレスリリース | 個人 | 小 | Phase 3 |
| ASO | 個人 | 小 | Phase 3 |
| イベント | グループ | 小（コスト過大） | Phase 3 |
| アプリ紹介メディア | 個人 | ほぼゼロ | やらない |
| Web広告 | 個人 | **マイナス**（金を捨てる） | やらない |
| App Store広告 | 個人 | **マイナス** | やらない |
| ユーザーコミュニティ運営 | — | ゼロ（ユーザーが居ない） | やらない |

**広告が「マイナス」なのは、費用が無駄になるからではない。**
1人ぼっちのグループを大量に作り、`GROWTH_STRATEGY.md` 0-1 の最悪シナリオ（「今日も自分」が7日続く）を大量生産して、**「このアプリはつまらない」という誤った結論をデータとして得てしまうから**である。

## 2. ゼロ週目の目標は「10万インプレッション」ではなく「20グループ」

Phase 0 の目標を数字で固定する。

```
S = 20 グループ
```

なぜ20か。

- **20グループ = 言い出しっぺ20人**。1人が手で声をかけられる現実的な上限がこのあたり
- 20グループあれば、R（週次継続率）と K（作品あたり新規グループ数）が**初めて意味のある精度で測れる**
- 20グループ × 3〜7人 = **60〜140人**。ここが Rotash の「最初の100人」

**注意：「20人のユーザー」ではなく「20人の言い出しっぺ」である。** ここを取り違えると、100人に配って1グループも成立しない、という結果になる。

そして20人は、広告では作れない。**手で作る。**

### 20グループは「テストユーザー」ではなく「20個の小さなメディア」

ここは考え方を変えたほうがいい。20グループは検証対象であると同時に、
**Rotash が持つ最初のコンテンツ制作ラインである。**

```
20グループ × 7日 = 最大 140 個の「実際の生活コンテンツ」
```

しかも広告代理店が作った素材ではなく、**本物の7日間**である。
Phase 0 は「検証期間」ではなく、**検証とコンテンツ生産が同時に走る期間**だと考える。

だから20グループは、同じ種類で揃えない。**わざとバラす。**

| グループ | 7日間の中身 |
|---|---|
| A | ライブまでの7日間 |
| B | 文化祭の準備週間 |
| C | 夏休み最後の7日 |
| D | 旅行前の1週間 |
| E | 部活の大会まで |
| F | ただの大学生活（対照群） |
| … | … |

**F のような「出来事のない週」を必ず1〜2つ混ぜる。**
出来事があるほうが強い、という仮説そのものを検証するには、比較対象が要る。
全部を出来事つきで固めると、「出来事が効いた」のか
「単に手で口説いたグループだから続いた」のかが分離できない。

## 3. どこから始めるか — 「何かに向かう1週間」を狙う

ここが、この3本の記事から得られる最も価値のある示唆である。

Rotash は「何でもない1週間」より、**「何かに向かう1週間」のほうが圧倒的に強い。**

```
弱い：ただの1週間
  月 自撮り  火 自撮り  水 自撮り  木 自撮り ...
  → 7人分の顔が並ぶだけ。「1週間」に見えない

強い：ライブまでの7日間
  月 チケット  火 グッズ  水 予習  木 ネイル
  金 前乗り    土 会場    日 余韻
  → 7枚に物語がある。誰が見ても意味が分かる
```

**この差は、Rotash 最大の未検証リスクを直接解決する。**

`PRODUCT_PHILOSOPHY.md` 5 / 21 / 22 で最重要検証項目とされているのは、
**「7分割の画角が狭く、写真が自撮りに偏るのではないか」** という問題だった。

「何かに向かう1週間」を狙うと、この問題が**機能を1つも足さずに緩和される**。撮る対象が最初から決まっているからだ。

> **ビーチヘッドの選択が、プロダクト最大のリスクをタダで下げる。**

### なぜ「向かう先」があると全部が解ける

| 問題 | 「向かう1週間」による解決 |
|---|---|
| 写真が単調になる | 撮る対象が日ごとに自然に変わる |
| 7人が集まらない | **その予定に一緒に行く人が、既にグループになっている** |
| 完成作品に物語がない | 7枚が「◯◯までの7日間」という筋を持つ |
| いつ始めればいいか分からない | 予定の7日前という明確な開始日がある |
| シェアする理由がない | **予定の当日は、元々みんな投稿する日** |

最後の行が特に効く。ライブ・旅行・文化祭の当日は、**誰もが元々SNSに投稿する日**である。そこに完成作品が乗る。宣伝しなくていい。

### 最初に狙う先（優先順）

1. **ライブ・フェスに一緒に行く友達グループ** — 「1.3万RT」の著者が持っていたのと同じコミュニティ。既にグループが存在し、日付が決まっていて、元々SNSに投稿する
2. **部活・サークルの大会 / 合宿 / 発表前の1週間** — 7人前後で、既に毎日会っている
3. **旅行に行くグループ** — 旅行そのものが7日でなくても、「旅行までの7日間」で成立する
4. **文化祭・学園祭の準備週間** — 撮る対象が毎日変わり、7人以上いる

**狙わない先：** 「写真好き」「Vlog好き」「SNS好き」「仲良し7人」。
前3つは個人の趣味であってグループではない。そして最後の「仲良し7人」も弱い。
**仲が良いことは、撮る理由にならない。**

### 大きいコミュニティは、1グループではなく複数グループの源になる

部活・ゼミ・クラスは 7人ではなく 20〜40人であることが多い。
定員7に対して人が多すぎるので、一見すると相性が悪く見える。**逆である。**

```
25人の部活
   ↓
7人 × 3グループ + 4人 × 1グループ
   ↓
同じ大会に向かう「4つの別の1週間」が並走する
   ↓
完成後、4つの作品が互いに見せ合われる
```

**1つのコミュニティから、外部リーチをまったく使わずに K > 1 が発生する。**
しかも4つのグループは互いを知っているので、作品が確実に見られる。

定員7は、この場面では制約ではなく**分割の単位**として働く。
「なんで私が入っていないの」が起きるのは、グループが1つしか作れないと
思われているときだけである。**枠が足りないなら、もう1つ立てればいい。**

### ただし：出来事ベースには、構造的な弱点が1つある

**出来事は終わる。**

ライブは開催される。旅行は帰ってくる。文化祭は片付く。
つまり「◯◯までの7日間」は、**7日目に理由そのものが消滅する。**

成長式に当てはめると、この弱点の形がはっきりする。

```
WCG(t+1) = WCG(t) × ( R + K ) + S(t)

  出来事は  S を上げる（グループが立ちやすい）
            K を上げる（作品に物語があり、当日は元々投稿する日）
            R を  下げる（翌週、一緒にいる理由が消えている）
```

**出来事ベースの GTM は、S と K を最大化しながら R を削る。**
これは「立ち上がりは最高だが、3週目に死ぬ」という失敗の典型的な形である。

さらに悪いことに、この弱点は `GROWTH_STRATEGY.md` の M3（完成の瞬間）と重なる。
完成の演出を強くするほど「終わった」という感覚が強まり、
**出来事の終わりと作品の完成が同じ日に重なって、二重の終止符になる。**

#### 塞ぎ方は3つ

**1. 完成画面を「終わり」ではなく「1本増えた」として見せる**

M3 の完成画面で、作品を単独で見せてはいけない。
**Memories の積層の一番上に、今週の1本が載る瞬間**として見せる。

```
     終わった、に見える            1本増えた、に見える

   ┌─────────────┐          ▐███|██|█|███|██▌   ← 先週
   │             │          ▐█|███|██|█|███▌   ← 先々週
   │  ■■■■■■■   │          ─────────────────
   │             │          ▐■■|■■|■|■■|■■▌   ← 今週（新しく載る）
   └─────────────┘
    作品が1つ、宙に浮く         列が1本伸びる
```

**2. 月曜の朝、何も言わずに「今日は◯◯」が届く**

これは既に `rollWeekIfNeeded()` + M4 で実装される。
出来事が終わっても、**Rotash は勝手に次の週を始めている。**
「もう終わったから」と誰かが言い出す機会を作らない。

**3. 出来事のない週を、意図的に1週だけ経験させる**

これが本当の検証項目である。

> **「出来事のない普通の1週間」でも完成するか。**

ここが Rotash の生死を分ける。
出来事がある週しか完成しないなら、Rotash は**イベント用ツール**であって、
週次の習慣ではない。それはそれで成立するプロダクトだが、
`GROWTH_STRATEGY.md` が前提としている R が根本から変わる。

**Phase 0 で最も注意して見るのは、各グループの「2週目」である。**
1週目（出来事あり）の完成率は高くて当然なので、そこを見ても何も分からない。

## 4. 未完成作品を、週の途中からシェアする

`GROWTH_STRATEGY.md` では「完成作品をブランド化してシェアする」を MUST に置いた。
**これは正しいが、半分しか使えていなかった。**

Rotash の作品は、月曜から日曜まで**毎日違う姿をしている**。そのどれもがシェアできる。

```
月曜  □ □ □ □ □ □ □   0 / 7   ← 招待になる
火曜  ■ □ □ □ □ □ □   1 / 7
水曜  ■ ■ ■ □ □ □ □   3 / 7   ← これが最も強い
木曜  ■ ■ ■ ■ □ □ □   4 / 7
日曜  ■ ■ ■ ■ ■ ■ ■   7 / 7   ← 作品になる
```

### なぜ「3 / 7」が最も強いのか

**完成品は答えであり、未完成品は問いだから。**

Wordle の絵文字グリッドが機能した最大の理由は「答えを明かさないこと」だった（`GROWTH_STRATEGY.md` E-1）。
7枚そろった作品は、それ自体が完結している。見た人は「きれいだね」で終われる。

**3/7 の作品は終わっていない。** 見た人は必ず考える。

- 「残りの4枚は誰が撮るの？」
- 「これ、来週どうなるの？」
- 「そもそも何のアプリ？」

**未完成であることが、そのまま「これ何？」の装置になっている。**

### さらに重要：これは招待とシェアを1つに統合する

`GROWTH_STRATEGY.md` では M1（招待画像）と M2（シェア画像）を別々の施策として並べた。**これは分けなくていい。**

> **同じ画像生成器が、0/7 では招待状になり、7/7 では作品になる。**

変わるのは「何枚埋まっているか」と「n / 7」の数字だけで、フォーマット・フチ・ワードマーク・メンバー名は全部同じである。

```
1つの生成器（1080 × 1920 / 9:16）
    ↓
┌────────────────────────────────┐
│  THIS WEEK の画面そのものを      │
│  「横帯 × 7」に組み直して縦に積む  │
│  足すのは ROTASH の1語だけ        │
└────────────────────────────────┘
    ↓                    ↓                ↓
 0/7 → 招待状      3/7 → 途中経過     7/7 → 作品
 「あと6枠」        「これ何？」        「完成」
```

見出し・週の日付・曜日・担当者名は、すでに `ThisWeekView` の構図に入っている。
**別の署名ブロックを足すのではなく、画面をそのまま出す。**
9:16 を第一形式にする理由（写真の横幅が 18% → 100% になる）は
[`GROWTH_STRATEGY.md`](GROWTH_STRATEGY.md) E-3 を参照。

**実装量が減り、効果が増える。** M1 と M2 は1つの作業になる。

### シェアの回数が変わる

| | 完成時のみ | 途中もシェア可 |
|---|---|---|
| 1グループ・1週あたりのシェア機会 | 1回 | **最大6回** |
| シェアする人 | 完成を見た人 | **その日撮った本人**（撮った直後が最も見せたい） |
| 「これ何？」の強さ | 中（完結している） | **強（未完成）** |

**撮った直後**というタイミングが効く。自分が撮った1枚が7分割に入った瞬間は、その週で最も「見せたい」瞬間である。ここに共有導線を置く。

ただし、**押し付けない**。撮影後に共有シートを自動で開くのは禁止（撮影の「即確定・確認画面なし」という体験を壊す）。7分割画面のどこかに、常に静かに存在するだけでいい。

## 5. 計測 — 実はもう全部 Firestore に入っている

Cube の記事から学ぶべきなのは「シェアボタンを付けた」ことではない。

> **施策を打つ前に GA4 を見て、「機能が無いのではなく、発見されていない」と特定したこと。**

順序が逆なら、彼は「Weeklyキューブがつまらないから作り直そう」と誤診していた。

**現在の Rotash には、計測コードが1行も存在しない。**

```
$ grep -rniE "analytics|logEvent|track\(|Amplitude|Mixpanel" --include=*.swift .
（出力なし）
```

つまり今のままリリースすると、**どこで壊れているか永久に分からない。**
`GROWTH_STRATEGY.md` で特定した2つの詰まり（招待・シェア）は、どちらも「静かに」起きる。データが無ければ「体験がつまらない」に誤診する。

### ただし、SDK を入れるのは後でいい

`FirestoreClient.swift` を読むと、**グループの全状態が JSON 1個として Firestore に保存されている。**

```swift
Field.payload: ["stringValue": payload]   // RemoteGroupState を丸ごと JSON 化
```

`RemoteGroupState` には members / currentWeek / archive / slots（`capturedAt` 付き）が全部入っている。

> **つまり、アプリを1行も変えずに、今日から読み取り専用スクリプトで集計できる。**

Firestore の全ドキュメントを舐めるだけで、以下が取れる。

| 取れるもの | どう出すか | 何が分かるか |
|---|---|---|
| **グループの人数分布** | `members.count` を集計 | **3人到達率** — 最大の詰まりが実際に起きているか |
| 週ごとの充填数 | `slots.filter(isFilled).count` | 完成率 / 何曜日で止まるか |
| **週をまたいだ継続** | `archive.count` の分布 | **R（週次継続率）** |
| 撮影の時刻分布 | `capturedAt` | 通知を何時に出すべきか |
| 途中参加の発生率 | メンバー数の週次変化 | 招待が後から効いているか |

**4つの補助指標のうち3つ（3人到達率・完成率・R）は、実装ゼロで今日から測れる。**

### アプリ側に足すべき計測は、たった1つ

測れないのは **K（作品あたり新規グループ数）** だけである。
これには招待リンクに発行元グループ ID を埋める必要があり、それは MUST の M1 に既に含まれている。

```
rotash://join/{CODE}?from={発行元グループID}
       ↓
参加時に from を保存 → Firestore の payload に含まれる
       ↓
K = 親グループ1つあたりの子グループ数
```

**追加の SDK は要らない。** 20グループ規模では、13個のイベントを取るより、Firestore を1回舐めて、**20人に直接聞くほうが精度が高い**。

イベント計測を本格的に入れるのは、グループが100を超えて「誰に聞けばいいか分からなくなってから」でいい。

### 「どの7日間が効いたか」は、いいね数では測れない

20グループをバラして走らせる目的は、**どの種類の1週間が新しいグループを生むかを知ること**である。
ここで測る指標を間違えると、Cube の著者が避けた誤診をそのまま踏む。

```
❌  ライブの投稿 → いいね 500 → 「ライブが効いた」
✅  ライブの投稿 → いいね 500 → 新規グループ 0 → 効いていない
    文化祭の投稿 → いいね 20  → 新規グループ 2 → こちらが効いた
```

**いいね・保存・リーチは、Rotash にとって全部ノイズである。**
見るべきは1つだけ ── **その投稿から実際に立ち上がったグループの数**。

これは M1 の招待リンクで測れる。

```
rotash://join/{CODE}?from={発行元グループID}

  → グループごとに固有の from を持つ
  → グループには「7日間の種類」のラベルを手で付けておく
  → 出来事の種類別に K が出る
```

| 7日間の種類 | グループ数 | 完成 | 新規グループ | K |
|---|---|---|---|---|
| ライブ・フェス | 4 | 4 | 3 | 0.75 |
| 文化祭・学園祭 | 3 | 3 | 4 | 1.33 |
| 旅行前 | 3 | 2 | 1 | 0.33 |
| **出来事なし（対照）** | **2** | **?** | **?** | **?** |

**この表が Phase 2 でどこに投資するかを決める。**
20グループという小さな規模でも、K が 1 を超える種類が1つでも見つかれば、
そこに絞って S を再開するだけで成長が始まる。

## 6. 「7人でやってみた」を、誰にやってもらうか

インフルエンサー施策について、1点修正する。

**「7人のインフルエンサーを集めて1週間やってもらう」は、失敗しやすい。**

理由は2つある。

1. **7日間の完走率が低い。** 案件として集められた7人は、生活を共有していない。1人が飛べば黒い穴が空き、**完走できなかった作品が広告として出る**。ゼロより悪い
2. **より根本的に、そこには関係がない。** Rotash の作品の価値は「この7人が同じ1週間を生きた」ことにある。集められた7人の1週間は、7枚の写真ではあっても、**Rotash の作品ではない**

> **正しいのは、「7人を集める」のではなく、「既に7人で動いている人たち」に渡すこと。**

- 既に仲間内で一緒に投稿しているグループ（バンド、ダンスチーム、配信者仲間、部活）
- フォロワー数ではなく、**「いつも一緒にいる人が映っているか」** で選ぶ

**Rotash におけるインフルエンサーの定義を、はっきり書き換える。**

| | 普通のアプリ | Rotash |
|---|---|---|
| 見る数字 | フォロワー数 | **一緒に活動している人数** |
| 強い人 | フォロワー10万人・単独で活動 | **フォロワー3,000人・いつも6人と活動** |
| 理由 | リーチが大きい | **その人が声をかけるだけでグループが成立する** |
| 出てくるもの | 紹介動画 | **その7人の日常そのもの** |

フォロワー10万人の単独クリエイターに依頼すると、7人を集めるところから始まる。
フォロワー3,000人でも既に6人と動いている人なら、**声をかけた瞬間にグループが立つ。**
そして完成する確率が高く、完成した作品には本物の関係が写っている。

これは、Setlog が「生活そのものへの憧れ」を広告にしたのと同じ構造である。
**Rotash が広告にできるのは「友達関係そのもの」であって、個人の影響力ではない。**

## 7. SNS発信は「アプリの宣伝」ではなく「コンセプトの検証」

「1.3万RT」の著者の一番実用的な提言はこれだった。

> 開発をする前にアイデアを拡散してみてはどうでしょうか。
> **逆に、アイデアが拡散されないということは、モノをつくっても拡散されないということなのかもしれません。**

Rotash はもう作ってあるので順序は違うが、**投稿の中身は「宣伝」ではなく「検証」にできる。**

```
弱い：
  「Rotash をリリースしました！友達と写真を撮れるアプリです」
  → 誰も反応しない。宣伝は無視される

強い：
  完成作品の画像を1枚置いて、
  「友達7人で1週間、1日1枚ずつ撮ったらこうなった」
  → 「これ何？」が起きる。アプリの名前すら要らない
```

**投稿するのはアプリではなく、作品である。**

そしてこの投稿は、同時に3つの仕事をする。

1. **コンセプト検証** — 「これ友達とやりたい」が出るか
2. **言い出しっぺの発見** — 反応した人が、そのまま S の候補になる
3. **クリエイティブの検証** — どの完成作品が反応を取るかが分かり、シェア画像の設計に返ってくる

反応が出なければ、**シェア画像の設計が間違っている**という情報が手に入る。

### 投稿の型 — アプリの話をしない

```
❌  新しい写真共有アプリ「Rotash」が登場！
❌  友達と7日間写真を撮ろう！
❌  App Store で公開しました

⭕  友達7人で1週間、1日1枚ずつ撮った。      ＋ 完成画像
⭕  ライブまであと7日。                     ＋ 3/7 の画像
⭕  この7枚、7人が1枚ずつ撮ってます。        ＋ 完成画像
⭕  あと3枚。                               ＋ 4/7 の画像
```

**キャプションにアプリ名は要らない。宣伝文も要らない。**

ただし1点だけ、「アプリ名すら要らない」を字義通りに取ってはいけない。
**画像の中の `ROTASH` の1語は必須である**（`GROWTH_STRATEGY.md` E-3）。

理由：「これ何？」が起きても、**答えにたどり着く手がかりが1つもなければ、
好奇心はその場で消える。** Wordle のグリッドが機能したのは、周囲の全員が
投稿していて名前が口伝で広まる状態だったからで、20グループの Rotash に
その前提はない。

> **キャプションでは宣伝しない。画像の中に固有名詞を1語だけ置く。**
> この2つは矛盾しない。

### 成功指標は「いいね」ではなく「相手の名前が出た人の数」

これが Phase 0 の SNS 発信で見るべき唯一の数字である。

投稿に反応があったら、こう返す。

> **「誰とやりたい？」**

そして、**具体的な相手が言えた人だけを数える。**

```
「面白そう」                       → 0
「やってみたい」                    → 0
「高校の友達6人でやりたい」          → 1  ← これだけが価値
「バイト先のみんなとやりたい」        → 1
```

**いいねが100個つくより、相手を名指しできる人が5人出るほうが価値が高い。**
前者は100人の観客で、後者は5グループ = 15〜35人の参加者だからである。

そしてこの5人は、そのまま **S の候補リスト**になる。
Phase 0 の SNS 発信は、拡散施策ではなく **言い出しっぺの採用面接**である。

### 何を「憧れ」として置くか

Setlog は「この人の生活、おしゃれだな」を作った。**個人の生活への憧れ**である。

Rotash が作れるのは違うものだ。

```
Setlog   個人  →  「こういう生活がしたい」    生活への憧れ
Rotash   7人   →  「この7人、何してるんだ？」  関係性への憧れ
```

若者が欲しいのは「自分がおしゃれになること」だけではない。
**「こういう友達関係が欲しい」**もある。そしてそちらは、
個人で完結するプロダクトには絶対に作れない。

だから投稿で見せるのは、きれいな写真ではなく **7人が写っている7日間**である。
写真の質が高い作品より、**関係が見える作品**を選んで出す。

## 8. Phase 設計

### Phase 0 — 手で20グループ（広告費ゼロ）

**目標：S = 20。R と K は測らない（母数が足りない）。**

やること：

1. **M1〜M5 を実装する**（`GROWTH_STRATEGY.md` L-1）— 特に招待リンクと画像生成器
2. **Firestore 集計スクリプトを書く**（読み取り専用・アプリ変更なし）
3. **言い出しっぺを20人、手で口説く** — 「アプリ使って」ではなく「今週これ、7人でやらない？」
4. **ビーチヘッドから始める** — ライブ / 合宿 / 文化祭など、既に日付がある予定に合わせる
5. **全グループを目で見る** — 20なら全部追える。20人にインタビューする（`PRODUCT_PHILOSOPHY.md` 30 の質問リスト）

**この段階で広告・PR・ASO・メディアは一切やらない。**

判定条件：

| 指標 | 撤退・再設計ライン | 次へ進むライン |
|---|---|---|
| 3人到達率 | 40%未満 → **招待が壊れている**。M1 をやり直す | 60%以上 |
| 1週目の完成率 | 40%未満 → **日次ループが回っていない**。M4 を見直す | 70%以上 |
| **2週目の完成率** | **1週目から半分以下に落ちる → 出来事が切れると死ぬ。R の前提が崩れている** | 1週目の 70%以上 |
| **出来事なし群の完成率** | ゼロに近い → **Rotash はイベント用ツールであって週次の習慣ではない**。戦略を組み直す | 出来事あり群と同水準 |
| 出来事別の K | どの種類も 0.1 未満 → **共有画像かシェア導線が壊れている** | 1種類でも 0.5 以上 |
| 写真の多様性 | 自撮りが7割超 → **画角の分離（LATER→MUST）** | 目視で判断 |

**このうち最重要は「2週目の完成率」と「出来事なし群」の2行である。**
1週目は手で口説いた直後で出来事もあるので、高くて当たり前で、何も分からない。

### Phase 1 — R と K を、S を止めて測る

**目標：`R + K > 1` が成立しているかを、正直に確かめる。**

ここで **S を意図的に止める**。手で作るのをやめて、ループだけで増えるかを見る。

```
S を止めた状態で
  WCG が横ばい以上  → R + K ≥ 1。ループが回っている
  WCG が減っていく  → R + K < 1。まだ穴がある
```

**これは怖いが、必ずやる。** S を混ぜたまま測ると、自分の労力をループの成果と誤認する。「1.3万RT」の著者が人脈で作った100RTを、アプリの魅力と誤認しないのと同じことである。

減っていたら、Phase 0 に戻って穴を塞ぐ。**ここで広告に逃げない。**

### Phase 2 — ループが回ってから、初めて外に出る

`R + K > 1` が確認できてから、初めて以下に投資する。

- インフルエンサー（既に7人で動いているグループに渡す）
- SNS発信の本格化
- コラボ（「◯◯までの7日間」という企画は、ビーチヘッドの拡張として自然）
- オフライン（学校・イベント）

**この順序を守る理由：** ループが `R + K < 1` のまま1000人連れてきても、1000人が抜けていくだけである。
**穴の空いたバケツに水を注ぐ量を増やしても、水は溜まらない。**

### Phase 3 — 最後に、効率の話

ASO / PR / アプリ紹介メディア / 広告。
ここまで来て初めて、「個人を連れてくる手法」にも意味が出る。ループが回っていれば、個人が入っても言い出しっぺに変わるからだ。

## 9. 追加で採用する仕様

この3本の記事から、新たに採用を決めるもの。

### 採用：週にタイトルをつける（SHOULD）

7枚が完成したとき、**7枚目を撮った人が、1行だけ**タイトルをつける。

```
「雨の日ばっかりだった」
「夏休み最後の週」
「意味わからん7日間」
```

**なぜ採用するか：**

- 7枚を「7枚の写真」から「1つの作品」に変える最小の手段。追加の機能ではなく**署名**である
- シェア画像に載る**唯一の人間の声**になる。これがあるから、シェア画像が自動生成の広告に見えない
- Memories が「日付の羅列」ではなく「タイトルの並び」になり、積層に意味が乗る
- **7枚目を撮った人**がつけるので、最後の撮影に小さな役割が生まれる（それまで最後の担当者には何もなかった）

**厳格な制約：**

| 制約 | 理由 |
|---|---|
| 1行のみ・20文字程度まで | 長文欄になった瞬間にキャプション機能になる |
| つけるのは7枚目を撮った1人だけ | 全員が書けるとコメント欄になる（**DON'T**） |
| 後から編集しない | その週の記録である |
| 空でも成立する | 必須にすると義務になる |
| 返信・リアクションは付けない | 作品への外部評価は **DON'T**（`GROWTH_STRATEGY.md` J-1） |

**タイトルは作品の署名であって、コメント欄ではない。** この一線を越えたら削除する。

### 確認：「前日の写真が次の人を動かす」は、すでに実装されている

「A の写真が B を動かし、B の写真が C を動かす」という連鎖について。

**これは新機能ではない。`ThisWeekView.swift` で既に実現されている。**

```swift
// 撮影中、ライブビューは自分の担当枠の中だけに出る。
// 他の枠には、それまでに撮られた写真がそのまま表示され続けている。
case .ready: CameraPreview(controller: camera)
```

撮る人は、**前の6日分の写真を横に並べたまま、自分の枠の中で構図を決める。**
つまり物理的に「前日の写真に返す」構造になっている。フルスクリーンのカメラを出していたら、これは成立しない。

> **この設計は Rotash の中核資産である。カメラを全画面にする変更は、いかなる理由でも入れない。**

「返事をする」ためのリアクション機能・スタンプは**不要**であり、追加すれば作品を評価の場に変える（**DON'T**）。既に構造が担っている。

### 不採用：シェアへの報酬

シェアしたらポイント・コイン・特典。**不採用。**

Rotash で欲しいのは「報酬のために宣伝する」ではなく「完成したから見せたい」である。
報酬を付けた瞬間、シェアが**作業**になり、シェア画像が**広告**として受け取られる。

**シェアへの唯一の報酬は、シェア画像そのものが欲しくなることである。**

## 10. まとめ — 更新された成長モデル

```
        WCG(t+1) = WCG(t) × ( R + K )  +  S(t)


  Phase 0 ── S がすべて。手で20グループ。広告費ゼロ。
             ビーチヘッド：「◯◯までの7日間」
             計測：Firestore を舐めるだけ（実装ゼロ）
                    │
                    ▼
  Phase 1 ── S を止めて、R + K を正直に測る
             ここで広告に逃げない
                    │
             R + K > 1 ?
              │        │
         いいえ        はい
              │        │
       Phase 0 へ戻る   ▼
       （穴を塞ぐ）  Phase 2 ── 外に出る
                            インフルエンサー / SNS / コラボ
                                    │
                                    ▼
                            Phase 3 ── ASO / PR / 広告
```

### 4行で

1. **`R + K > 1` は、ループに何かが乗ってから初めて意味を持つ式である。最初の1周は手で作るしかない。**
2. **獲得の単位は「6人を呼べる1人 × 7日間の理由がある出来事」。だから広告はゼロ週目には有害ですらある。**
3. **20グループは検証対象であると同時に、最初の20個のメディアである。だから種類をわざとバラし、出来事別に K を出す。**
4. **ただし出来事は終わる。S と K を上げる代わりに R を削るので、Phase 0 で最も見るべきは「2週目」と「出来事のない週」である。**

### 最初の100人を集めるのではなく、最初の20個の物語を作る

これが Phase 0 の全てである。

Setlog が「何を共有したくなるか」を、Cube が「どう誤診を避けるか」を、
「1.3万RT」が「最初の火をどう作るか」を、15手法の記事が「火がついた後に何ができるか」を教えている。
4本は次の順序で1本につながる。

```
1.3万RT   →  0→100 は人力。20人の言い出しっぺを手で口説く
Setlog    →  何を見せるか。作品ではなく「関係性への憧れ」を見せる
Cube      →  感覚で改善しない。出来事別に K を測り、当たりを特定する
15手法    →  当たりが分かってから、そこにだけ外部施策を投入する
```

**Rotash は「アプリをバズらせる」のではなく、「7人の1週間をバズらせる」。**
